Kubernetes Interview Cheatsheet

32 essential Kubernetes interview questions covering core concepts, networking, security, troubleshooting, and advanced patterns.

Section 01

Core Concepts

Core Concepts

Explain Services and the different service types

Services provide stable network endpoints to pods. Different types expose applications differently to enable external access.

Q&AService types›
ClusterIP (Default)
  • Internal-only service, accessible within cluster
  • Assigns stable IP (10.0.0.1 or similar)
  • DNS: my-service.default.svc.cluster.local
  • Use for: pod-to-pod communication
NodePort
  • Exposes on every node's port (30000-32767)
  • External clients access: node-ip:30001
  • Also has ClusterIP internally
  • Use for: external access without load balancer
LoadBalancer
  • Creates cloud load balancer (AWS ELB, Azure LB)
  • Assigns external IP automatically
  • Use for: exposing apps to internet
  • Cost: expensive if many services
ExternalName
  • DNS CNAME alias to external service
  • No load balancing, just DNS redirection
  • Use for: integrating external services
Say this in interview "ClusterIP for internal communication. NodePort for basic external access. LoadBalancer for production. For multiple services, use Ingress instead—it's cheaper and better."
Core Concepts

What's the difference between Deployments, StatefulSets, and DaemonSets?

These are three different workload types for different use cases. Understanding when to use each one is critical for production deployments.

Q&AWorkload types›
Deployments
  • Stateless applications (web servers, APIs)
  • Pods are interchangeable and replaceable
  • ReplicaSet manages desired number of replicas
  • Rolling updates: gradually replace old pods with new ones
  • No guaranteed pod ordering or unique identity
  • Example: nginx web server, Python API
StatefulSets
  • Stateful applications (databases, message queues)
  • Pods have stable, unique identity (pod-0, pod-1, pod-2)
  • Stable hostname: mysql-0.mysql-svc.default.svc.cluster.local
  • Pods are ordered and launched sequentially
  • Each pod has persistent storage (PVC)
  • Example: MySQL, Elasticsearch, Kafka
DaemonSets
  • Runs one pod per node (or subset of nodes)
  • Always present on target nodes
  • No replicas to manage; K8s handles placement
  • Good for: monitoring agents, logging, networking
  • Example: Prometheus node-exporter, Fluentd logging agent
Say this in interview "Deployments for stateless apps like web servers. StatefulSets for stateful apps like databases—pods get stable names and hostnames. DaemonSets run one pod per node for monitoring agents."
Core Concepts

What's an Ingress controller? How does it differ from LoadBalancer?

Ingress is the preferred way to expose multiple services externally. One Ingress replaces many LoadBalancers.

Q&AHTTP/HTTPS routing›
LoadBalancer vs Ingress
  • LoadBalancer: One service = one cloud LB = one IP
  • Ingress: Multiple services = one LB = one IP
  • Ingress is cheaper and better for routing
Ingress Controller
  • Software that reads Ingress resources and configures routing
  • Popular: Nginx, HAPROXY, Traefik, Kong
  • Runs as pod in cluster
  • Watches Ingress resources and updates configuration
Traffic Flow
  • Client → DNS → Ingress Service (LB) → Ingress Controller Pod → Service → Pod
  • Controller reads: hostname, path, TLS cert
  • Routes to correct backend service
Say this in interview "Ingress is a single entry point for multiple services. One controller replaces many LoadBalancers. I define routing by hostname and path. Cheaper and more maintainable."
Core Concepts

Explain traffic flow from external client to pod through Ingress

Understanding the request journey is critical for debugging network issues.

Q&ARequest path›
Flow Steps
  • 1. DNS resolves hostname to Ingress IP
  • 2. Client sends HTTP request to Ingress IP
  • 3. Cloud LB forwards to Ingress controller pod
  • 4. Controller reads hostname and path
  • 5. Controller forwards to correct Service (ClusterIP)
  • 6. Service load balances to available pods
  • 7. Pod processes request and responds
  • 8. Response flows back through same chain
Debugging
  • DNS not resolving? Check DNS provider
  • Connection refused? Controller pod running?
  • Wrong backend? Check Ingress routing rules
  • Timeout? Check service endpoints: kubectl get endpoints
  • Pod not responding? kubectl logs pod-name
Say this in interview "DNS → Ingress IP → LB → Controller → Service → Pod. If broken, I check each step: DNS, LB, controller pod, service endpoints, pod logs."
Core Concepts

What's the purpose of ConfigMap vs Secret?

Both pass data to pods, but for different types of data. ConfigMap for config, Secret for sensitive data.

Q&AConfiguration management›
ConfigMap
  • Non-sensitive configuration data
  • Stored as plain text (NOT encrypted)
  • Key-value pairs or files
  • Example: log-level=debug, app-mode=production
  • Size limit: 1MB per ConfigMap
Secret
  • Sensitive data (passwords, API keys, tokens)
  • Base64 encoded by default (NOT encrypted unless configured)
  • Can enable encryption at rest in etcd
  • Example: passwords, JWT tokens, TLS certs
  • Size limit: 1MB per Secret
Usage
  • Inject as env vars: valueFrom.configMapKeyRef / secretKeyRef
  • Mount as files: volumes and volumeMounts
  • ConfigMap for app settings, Secret for credentials
Say this in interview "ConfigMap for non-sensitive settings like log levels. Secret for passwords and API keys. Both can be env vars or volume mounts. Important: enable encryption at rest in etcd for production."
Section 03

Networking

Networking

Explain how networking works in Kubernetes (pod-to-pod, pod-to-service, external traffic)

K8s networking is complex but logical. Every pod gets its own IP and can talk to other pods directly.

Q&ANetwork model›
Pod-to-Pod Communication
  • Every pod gets unique IP (from pod CIDR range)
  • Pods on same node: communicate directly via veth pairs
  • Pods on different nodes: CNI plugin routes traffic (Flannel, Calico, Weave)
  • No NAT or translation: direct IP-to-IP
Pod-to-Service Communication
  • Service has stable IP (ClusterIP: 10.0.0.5)
  • kube-proxy on each node creates iptables rules
  • Traffic to Service IP redirected to pod IP
  • Load balanced across all matching pods
External Traffic
  • LoadBalancer Service: cloud LB → node:port → service → pod
  • NodePort: client:node-port → service → pod
  • Ingress: DNS → LB → ingress controller → service → pod
Say this in interview "Every pod has unique IP. Pods talk directly (no NAT). CNI plugin routes between nodes. Service IP is stable but virtual—kube-proxy redirects traffic. LoadBalancer/Ingress expose to external traffic."
Networking

What's a Network Policy? How do you implement network segmentation?

Network Policies are K8s firewalls. Default: all pods can talk to all pods. NetworkPolicy restricts this.

Q&AMicro-segmentation›
Default Behavior
  • All pods can communicate with all pods (no restrictions)
  • Risky for security (lateral movement if pod compromised)
  • Need to explicitly allow traffic with NetworkPolicy
NetworkPolicy Example
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-frontend-to-database
spec:
  podSelector:
    matchLabels:
      tier: database
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          tier: backend
    ports:
    - protocol: TCP
      port: 5432

# Result: Only backend pods can reach database
# Frontend pods blocked
Best Practices
  • Deny all ingress by default, allow specific traffic
  • Separate namespaces for different apps (tenant isolation)
  • Allow ingress only from known sources
  • Allow egress to known destinations (internal services, external APIs)
Say this in interview "NetworkPolicies are K8s firewalls. Default allows all traffic. I create policies to deny unnecessary traffic: frontend can't reach database, frontend can't reach admin, etc. Essential for multi-tenant clusters."
Networking

How does DNS work in Kubernetes? Explain service discovery

K8s includes built-in DNS. Services get DNS names automatically. This enables service discovery without external tools.

Q&AService discovery›
DNS Components
  • CoreDNS pod runs in kube-system namespace
  • Watches Service resources and creates DNS records
  • kubelet configures pods to use CoreDNS
  • Pods query CoreDNS for service IPs
Service DNS Names
  • Format: service-name.namespace.svc.cluster.local
  • Example: mysql.default.svc.cluster.local → 10.0.0.5
  • Short form within namespace: mysql (CoreDNS expands to full name)
  • Each service gets A record pointing to ClusterIP
Service Discovery Flow
  • 1. Pod app.yaml needs to connect to database
  • 2. App queries DNS: mysql.default.svc.cluster.local
  • 3. CoreDNS responds: 10.0.0.5 (mysql service IP)
  • 4. App connects to 10.0.0.5:5432
  • 5. kube-proxy redirects to actual database pod
Say this in interview "K8s automatically creates DNS records for services. Apps query CoreDNS to discover services by name. No manual service registry needed. Short names work within namespace."
Networking

What's a service mesh (Istio, Linkerd)? When would you use one?

Service mesh adds advanced networking features: traffic management, security policies, observability.

Q&AAdvanced traffic management›
What It Does
  • Injects sidecar proxies into every pod
  • Proxies intercept all network traffic
  • Provides: traffic routing, load balancing, circuit breaking, retries
  • Also: mTLS encryption, rate limiting, distributed tracing
When to Use
  • Large, complex microservices architectures
  • Need for advanced traffic management (canary, A/B testing)
  • Security: enforce mTLS between all services
  • Observability: automatic metrics and tracing
When NOT to Use
  • Small, simple clusters (overhead not worth it)
  • Performance-critical: adds latency (sidecar proxies)
  • Learning cluster: too much complexity
Popular Options
  • Istio: most feature-rich, complex
  • Linkerd: lightweight, easy to operate
  • Consul: service mesh + service registry
Say this in interview "Service mesh adds sophisticated traffic management: canary deployments, automatic retries, circuit breaking. Enables mTLS between services. Adds observability. But adds complexity and latency. Use only for large, complex clusters."
Networking

What's the difference between CNI plugins? Which have you used?

CNI plugins provide pod-to-pod networking. Different plugins have different capabilities and performance.

Q&ANetworking implementations›
Popular CNI Plugins
  • Flannel: Simple overlay, encapsulates traffic (VXLAN)
  • Calico: Advanced policies, BGP routing, performance-focused
  • Weave: Mesh networking, encrypted by default
  • Azure CNI: Uses Azure VNet, better performance
  • AWS VPC CNI: Native VPC networking
Flannel
  • Simple, easy to setup
  • Overlay network (encapsulates traffic)
  • Lower performance (extra packet overhead)
  • Good for: learning, small clusters
Calico
  • Advanced, production-ready
  • Native routing (no overlay)
  • Integrates with network policies
  • Better performance than Flannel
  • Good for: large, performance-sensitive clusters
Cloud-Native (Azure CNI, AWS VPC CNI)
  • Use cloud provider's network infrastructure
  • Pod gets real cloud VNet IP (not overlay)
  • Best performance
  • Only works on that cloud provider
Say this in interview "Flannel is simple but slow (overlay). Calico is fast and feature-rich. Cloud-native CNIs (Azure, AWS) are fastest because pods use real VNet IPs. I choose based on: performance needs, multi-cloud vs single-cloud, policy requirements."
Networking

How do you route traffic based on hostnames and paths with Ingress?

Ingress enables sophisticated routing without multiple load balancers.

Q&AHTTP routing›
Hostname-based Routing
  • Route to different services based on Host header
  • api.example.com → API service
  • admin.example.com → Admin service
  • One IP, multiple domains
Path-based Routing
  • Route based on URL path
  • /api → API service
  • /static → Static files service
  • Same hostname, different paths
Ingress Example
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-host
spec:
  rules:
  # Hostname routing
  - host: api.example.com
    http:
      paths:
      - path: /
        backend:
          service:
            name: api-service
            port:
              number: 8080

  # Path routing
  - host: example.com
    http:
      paths:
      - path: /api
        backend:
          service:
            name: api-service
            port:
              number: 8080
      - path: /static
        backend:
          service:
            name: static-service
            port:
              number: 80
Say this in interview "Ingress routes by hostname and path. Host header determines which domain → which service. Path determines which endpoint → which service. One Ingress can route to many services."

Storage

How do you mount Secrets and ConfigMaps as volumes vs environment variables?

Two different ways to inject data. Each has tradeoffs for updates, visibility, and file-based configs.

Q&AInjection methods›
Environment Variables
  • Injected at pod startup, static after that
  • Changes to ConfigMap/Secret require pod restart
  • Good for: small values, simple configuration
  • Bad for: large files, dynamic updates
Volume Mounts
  • Mounted as files in container filesystem
  • Updates to ConfigMap/Secret reflected within seconds
  • Good for: configuration files, dynamic updates
  • Bad for: binary data, very large files
Example
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  containers:
  - name: app
    image: myapp:latest

    # Method 1: Environment variables
    env:
    - name: LOG_LEVEL
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: log-level
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: password

    # Method 2: Volume mount
    volumeMounts:
    - name: config-volume
      mountPath: /etc/config
    - name: secret-volume
      mountPath: /etc/secrets

  volumes:
  - name: config-volume
    configMap:
      name: app-config
  - name: secret-volume
    secret:
      secretName: db-secret
Say this in interview "Use env vars for simple values. Use volume mounts for configuration files and when you need dynamic updates. Volume mounts auto-update when ConfigMap/Secret changes; env vars don't."
Storage

What's storage class and how does it relate to dynamic provisioning?

StorageClass enables automatic volume creation with specific properties. No manual PV creation needed.

Q&ADynamic volumes›
Without StorageClass (Manual)
  • Admin creates PersistentVolume (PV) manually
  • User creates PersistentVolumeClaim (PVC) requesting it
  • Matching PV and PVC bound together
  • Slow and tedious at scale
With StorageClass (Dynamic)
  • StorageClass defines volume properties (type, performance, encryption)
  • User creates PVC specifying StorageClass
  • K8s automatically creates PV from that class
  • No manual PV creation needed
Example
# StorageClass definition
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: azure.com/disk
parameters:
  type: Premium_LRS
  cachingmode: ReadWrite

# PVC using StorageClass
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 100Gi

# PV is automatically created from StorageClass
Say this in interview "StorageClass automates PV creation. Define StorageClass with volume properties (SSD, encryption, performance). User creates PVC specifying the class. K8s provisions the volume automatically."

Security & Access Control

Security

How do you enforce Pod Security Standards/Policies?

Pod Security Standards restrict what containers can do. Essential for multi-tenant clusters and compliance.

SecurityPod hardening›
Three Levels
  • Privileged: No restrictions (dangerous)
  • Baseline: Minimum security, prevents escalation
  • Restricted: Strict, production-grade security
Enforcing Standards
  • Label namespace: pod-security.kubernetes.io/enforce=restricted
  • Pods must comply or fail to create
  • Also: audit mode (log violations), warn mode (warn but allow)
Restricted Standards Require
  • runAsNonRoot: true (no root user)
  • readOnlyRootFilesystem: true (no write access)
  • allowPrivilegeEscalation: false
  • Drop all Linux capabilities
  • No hostNetwork or hostPID
Say this in interview "Enforce Pod Security Standards at namespace level. Use 'restricted' for production. Prevents privilege escalation, root access, excessive capabilities. Audit mode for testing, enforce mode for production."
Security

What's the difference between ServiceAccount and User authentication?

ServiceAccounts authenticate pods; Users authenticate people. Two different credential systems.

Q&AAuthentication types›
ServiceAccount (Pods)
  • Used by pods to authenticate to API server
  • Token mounted at /var/run/secrets/kubernetes.io/serviceaccount/token
  • Automatic per-pod credential
  • Scoped to namespace
  • Used with RBAC for access control
User (Kubectl/Humans)
  • Used by people running kubectl
  • Authenticated via: certificates, OAuth, OIDC, static tokens
  • Configured in kubeconfig file
  • Cluster-wide (not scoped to namespace)
  • Also controlled by RBAC
Use Cases
  • ServiceAccount: app needs to query K8s API (check services, get secrets)
  • User: DevOps engineer needs to deploy apps, check pods, etc.
Say this in interview "ServiceAccounts for pods, Users for humans. Each pod gets a ServiceAccount token automatically. Both are controlled by RBAC. ServiceAccounts are namespace-scoped, Users are cluster-wide."
Security

How do you implement least privilege for pods?

Least privilege minimizes damage if a pod is compromised.

SecurityMinimize blast radius›
Linux Capabilities
  • Drop ALL capabilities: - ALL
  • Add back only what's needed: NET_BIND_SERVICE
  • Prevents container from: changing system settings, raw socket access
Filesystem
  • readOnlyRootFilesystem: true
  • Container can't modify /
  • Allow /tmp and /var/run (emptyDir volumes)
User & Privileges
  • runAsNonRoot: true (no root access)
  • allowPrivilegeEscalation: false (can't gain privileges)
  • runAsUser: 1000 (specific non-root user)
Example Pod
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  containers:
  - name: app
    image: myapp:latest
    securityContext:
      runAsNonRoot: true
      runAsUser: 1000
      readOnlyRootFilesystem: true
      allowPrivilegeEscalation: false
      capabilities:
        drop:
        - ALL
        add:
        - NET_BIND_SERVICE
    volumeMounts:
    - name: tmp
      mountPath: /tmp
  volumes:
  - name: tmp
    emptyDir: {}
Say this in interview "Non-root user, read-only filesystem, drop all capabilities, no privilege escalation. Pod can't modify system, can't gain root, minimal blast radius if compromised."
Security

How do you manage secrets securely? (encryption, external managers)

Secrets in etcd are base64 encoded by default (NOT encrypted). Production needs real encryption and external managers.

SecuritySecret protection›
Problem
  • K8s Secrets are base64 encoded, not encrypted
  • Base64 is easily decoded (not secure)
  • Anyone with etcd access can read secrets
  • Secrets visible in kubectl logs
Solutions
  • Encryption at rest: Enable in API server config
  • External secret manager: AWS Secrets Manager, Azure Key Vault, HashiCorp Vault
  • External Secrets Operator: Syncs external secrets to K8s Secrets
Best Practice: External Manager
  • Store secrets in vault (AWS, Azure, Vault)
  • Pod fetches secret at runtime (not stored in etcd)
  • Secret never in K8s Secrets
  • Rotate secrets in vault, pod gets new one on restart
RBAC for Secrets
  • Restrict who can read Secrets
  • Default: anyone with pod access can read mounted secrets
  • Use ServiceAccount RBAC to limit secret access
Say this in interview "Never rely on K8s Secrets alone. Enable encryption at rest. Better: use external vault (AWS, Azure, Vault). Pod fetches secret at runtime. Rotate secrets regularly. RBAC to limit who can access."
Security

Explain network segmentation and zero-trust in Kubernetes

Zero-trust: never trust traffic by default. Explicitly allow only necessary communication.

SecurityLeast-privilege networking›
Zero-Trust Principles
  • Deny all by default (ingress and egress)
  • Explicitly allow necessary traffic only
  • Verify every connection (mTLS)
  • Segment by namespace, pod labels
NetworkPolicy Strategy
  • 1. Deny all ingress: kind: NetworkPolicy with empty 'from'
  • 2. Allow frontend from load balancer
  • 3. Allow backend from frontend
  • 4. Allow database from backend
  • 5. Explicit egress: only to required services
mTLS (Mutual TLS)
  • Both pod certificates validated (not just server)
  • Encrypt all inter-pod traffic
  • Implemented via service mesh (Istio, Linkerd)
  • Prevents man-in-the-middle attacks
Say this in interview "Zero-trust: deny all, allow only necessary. Use NetworkPolicies for network segmentation. Implement mTLS between services. Segment by namespace and pod labels. Verify all connections."
Security

What's Workload Identity Federation and how does it work?

Workload Identity lets pods use cloud credentials without storing secrets in K8s.

SecurityPod cloud auth›
Problem
  • Pod needs AWS/Azure credentials to access cloud resources
  • Storing credentials as K8s Secrets is risky
  • Credentials might leak or be exposed
Solution: Workload Identity
  • Link K8s ServiceAccount to cloud IAM role
  • Pod uses ServiceAccount token to assume IAM role
  • Pod gets temporary AWS/Azure credentials (no secrets stored)
  • Credentials auto-refresh
Azure Workload Identity Example
  • 1. Create Azure AD application
  • 2. Create K8s ServiceAccount
  • 3. Link ServiceAccount to AD app (federated identity)
  • 4. Pod uses ServiceAccount token to authenticate
  • 5. Pod assumes Azure role, gets credentials
Benefits
  • No secrets stored in K8s (secure)
  • Automatic credential rotation
  • Granular RBAC per pod/ServiceAccount
Say this in interview "Workload Identity removes secrets from K8s. Pod uses ServiceAccount token to assume cloud IAM role. Credentials temporary and auto-rotated. More secure than storing secrets."

How do you scan container images for vulnerabilities in K8s?

Image scanning catches vulnerable dependencies before deployment.

SecurityVulnerability detection›
Scanning Points
  • CI/CD: Before image build (fail if vulnerabilities)
  • Registry: Continuous scanning of stored images
  • Admission controller: Block deployment of vulnerable images
Scanning Tools
  • Trivy: Fast, free, accurate
  • Snyk: Online, detailed reports
  • Grype: Free, community-supported
  • Docker Scout: Built-in, easy to use
Enforcement
  • CI/CD: fail build if critical CVE detected
  • Registry: tag images with scan results
  • Admission webhook: reject pod if image has critical CVE
  • Policy Engine (OPA): enforce image scan requirements
Say this in interview "Scan images in CI/CD (fail build if critical CVE). Scan images in registry continuously. Use admission controller to block vulnerable images. Trivy or Snyk for scanning."

Monitoring & Observability

Monitoring

Explain liveness probes, readiness probes, and startup probes

Probes tell K8s when pods are healthy. Essential for automatic recovery and deployment safety.

Q&AHealth checks›
Readiness Probe
  • Is the pod ready to receive traffic?
  • Fails: pod removed from service (no traffic)
  • When to fail: app warming up, dependencies unavailable, degraded
  • Example: HTTP GET /health, should return 200
Liveness Probe
  • Is the pod still alive? Or is it hung?
  • Fails: pod is restarted
  • When to fail: deadlock, infinite loop, memory exhaustion
  • Example: HTTP GET /status, heartbeat check
Startup Probe
  • Has the app finished starting up?
  • Liveness/readiness only checked after startup succeeds
  • When to use: slow startup time (databases, compiling)
  • Prevents pod restart during startup
Example
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
  - name: app
    image: myapp:latest

    # App takes time to start
    startupProbe:
      httpGet:
        path: /startup
        port: 8080
      initialDelaySeconds: 0
      periodSeconds: 10
      failureThreshold: 30  # 300 seconds max

    # Is app ready for traffic?
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 10
      periodSeconds: 5

    # Is app alive?
    livenessProbe:
      httpGet:
        path: /alive
        port: 8080
      initialDelaySeconds: 30
      periodSeconds: 10
Say this in interview "Readiness: is pod ready for traffic? Liveness: is pod alive? Startup: is pod finished starting? Implement all three. Readiness prevents traffic to unavailable pods. Liveness restarts dead pods. Startup prevents restart during slow startup."
Monitoring

How do you collect and analyze logs from Kubernetes pods?

Pod logs are ephemeral (deleted with pod). Need centralized logging for production.

Q&ALog aggregation›
Pod Logs (Temporary)
  • kubectl logs pod-name (last 100 lines)
  • kubectl logs -f pod-name (follow logs)
  • Logs deleted when pod deleted
  • Not searchable or analyzable at scale
Centralized Logging Stack
  • Fluent Bit/Fluentd: Collect logs from pods
  • Elasticsearch: Store and index logs
  • Kibana: Search and visualize logs
  • Or: Loki (simpler), Splunk, ELK stack
Log Collection
  • 1. Fluent Bit DaemonSet on every node
  • 2. Reads /var/log/pods/*/*.log (pod logs)
  • 3. Enriches with pod metadata (labels, namespace)
  • 4. Sends to Elasticsearch/Loki
  • 5. Searchable via Kibana/Grafana
Say this in interview "kubectl logs for quick debugging. Centralized logging for production (ELK, Loki, Splunk). Fluent Bit collects logs and sends to central store. Logs enriched with pod metadata (namespace, labels). Searchable and analyzable."
Monitoring

What are SLI, SLO, and SLA? How do you define them for Kubernetes apps?

SLI/SLO/SLA define reliability expectations and budgets.

Q&AReliability targets›
Definitions
  • SLI (Service Level Indicator): Metric (e.g., 99.5% requests successful)
  • SLO (Service Level Objective): Target SLI (e.g., aim for 99.5%)
  • SLA (Service Level Agreement): Legal contract, penalties if missed
Common SLIs
  • Availability: % of time service is up
  • Latency: p99 request time (<100ms)
  • Error rate: % of requests that fail (<0.5%)
  • Throughput: requests per second
Error Budget
  • If SLO is 99.5%, error budget = 0.5% per month
  • Can use budget for maintenance (planned downtime)
  • Once budget exhausted, must prioritize reliability
Implementation
  • 1. Define SLOs (e.g., 99.5% availability)
  • 2. Measure SLIs with Prometheus/Grafana
  • 3. Monitor error budget burn rate
  • 4. Alert if burning too fast
Say this in interview "SLI is the metric, SLO is the target. Define SLOs: 99.5% availability, <100ms p99 latency, <0.5% error rate. Measure with Prometheus. Track error budget—if burning fast, prioritize reliability over features."
Monitoring

How do you set up distributed tracing in Kubernetes?

Distributed tracing shows request flow across microservices. Essential for debugging in complex systems.

Q&ARequest tracing›
Problem
  • Microservices: request touches frontend → backend → database → cache
  • One slow service affects everything
  • Hard to find bottleneck without distributed tracing
Solution: Distributed Tracing
  • Trace ID assigned to request at entry
  • Trace ID passed through all services (headers, metadata)
  • Each service reports spans (start/end of operation)
  • Jaeger/Zipkin collect and visualize traces
Implementation
  • Instrumentation: App adds tracing SDK (OpenTelemetry)
  • Collector: OpenTelemetry collector on DaemonSet
  • Backend: Jaeger (self-hosted) or Datadog/NewRelic (SaaS)
  • Service mesh: Istio/Linkerd auto-instruments traffic
Say this in interview "Use OpenTelemetry for instrumentation. Jaeger or Datadog as backend. Service mesh (Istio) can auto-trace. See request flow across services, find bottlenecks, debug latency."

Understand pod failure states and debugging

Different failure states indicate different problems. Knowing each state helps diagnosis.

Q&AFailure diagnosis›
Pending
  • Pod waiting to be scheduled
  • Causes: no resources, NodeSelector mismatch, image not pulled yet
  • kubectl describe: check Events and Node status
ImagePullBackOff
  • Can't pull image from registry
  • Causes: wrong image name, image doesn't exist, no pull credentials
  • Fix: check image URL, add imagePullSecrets
CrashLoopBackOff
  • App crashes on startup, K8s restarts it, crashes again (loop)
  • Causes: app error, missing dependencies, bad config
  • kubectl logs --previous to see crash logs
Init:Error
  • Init container failed
  • Causes: init container logic error, missing volume, failed command
  • kubectl logs -c init-container-name
CreateContainerConfigError
  • Container config invalid
  • Causes: bad volume mount, missing ConfigMap/Secret, bad command
  • kubectl describe: check Events for details
Evicted
  • Pod removed from node (node out of resources)
  • Causes: memory/disk pressure, node cordoned
  • kubectl describe: shows eviction reason
  • Fix: free resources or add nodes
Terminating (stuck)
  • Pod waiting to terminate (finalizers, graceful shutdown)
  • Causes: finalizers waiting, long gracePeriod
  • Force delete: kubectl delete pod --grace-period=0 --force
Exit Codes
  • Exit 0: success (normal termination)
  • Exit 1-128: app error
  • Exit 137: OOMKilled (memory limit exceeded)
  • Exit 143: SIGTERM (graceful shutdown)
Say this in interview "Pending = resource/scheduling issue. ImagePullBackOff = image problem. CrashLoopBackOff = app error. Init:Error = init container failed. Evicted = node out of resources. Each state has specific causes and fixes."

Explain node affinity and pod affinity. When do you use them?

Control where pods are scheduled. Affinity = prefer, anti-affinity = avoid.

Q&APod placement›
Node Affinity
  • Schedule pod on specific nodes
  • Example: GPU nodes, high-memory nodes
  • requiredDuringSchedulingIgnoredDuringExecution: must match
  • preferredDuringSchedulingIgnoredDuringExecution: nice to have
Pod Affinity
  • Schedule pods together or apart
  • Example: database + cache same node (performance)
  • Example: replicas on different nodes (HA)
Pod Anti-Affinity
  • Keep pods apart (avoid same node)
  • Example: multiple replicas on different nodes
  • Improves availability (node failure doesn't kill all replicas)
Use Cases
  • Node affinity: GPU tasks, memory-intensive, specific hardware
  • Pod affinity: latency-sensitive (keep together)
  • Pod anti-affinity: availability (spread replicas)
Say this in interview "Node affinity to schedule on specific nodes (GPU, high-memory). Pod anti-affinity to spread replicas across nodes (HA). Pod affinity to colocate related pods (performance)."

How do you perform zero-downtime deployments?

Update apps without dropping traffic. Multiple strategies.

Q&ADeployment strategies›
Rolling Update (Default)
  • Gradually replace old pods with new ones
  • maxSurge: max new pods (e.g., 1)
  • maxUnavailable: max pods down (e.g., 0)
  • Always has healthy pods running
Key Requirements
  • Pod readiness probe: new pod marked ready before receiving traffic
  • Pod preStop hook: time to gracefully shut down
  • terminationGracePeriodSeconds: wait time before force kill
  • Multiple replicas: don't deploy 1-pod app (no HA)
Example
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  replicas: 3  # Multiple replicas for HA
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

  template:
    spec:
      containers:
      - name: app
        image: app:v2

        readinessProbe:
          httpGet:
            path: /ready
            port: 8080
          initialDelaySeconds: 10

        lifecycle:
          preStop:
            exec:
              command: ["/bin/sh", "-c", "sleep 15"]  # Time to drain

      terminationGracePeriodSeconds: 30
Say this in interview "Rolling update: gradually replace pods. Set maxUnavailable=0 (always have pods). Use readiness probe to ensure new pod ready. preStop hook for graceful shutdown. Multiple replicas for HA."

What's a taint and toleration? When do you use them?

Taints repel pods; tolerations allow pods on tainted nodes. For node exclusion and workload isolation.

Q&ANode scheduling control›
Taint
  • Mark node: "no pods allowed unless they tolerate me"
  • Format: kubectl taint nodes node-name key=value:effect
  • Effect: NoSchedule (no new pods), NoExecute (evict existing)
Toleration
  • Pod says: "I can tolerate this taint"
  • Allows pod to schedule on tainted node
  • Defined in pod spec
Use Cases
  • GPU nodes: taint with gpu=true, only ML jobs tolerate
  • Dedicated nodes: taint with workload=special, only special jobs run there
  • Maintenance: taint node, evict non-critical pods, update safely
Example
# Taint GPU node
kubectl taint nodes gpu-node gpu=true:NoSchedule

# Pod toleration
tolerations:
- key: gpu
  operator: Equal
  value: "true"
  effect: NoSchedule
Say this in interview "Taints keep pods off nodes. Tolerations allow specific pods on tainted nodes. Use for: GPU nodes, dedicated workloads, maintenance windows."

How do you handle graceful pod termination?

Pod termination needs time for cleanup. Improper termination causes data loss.

Q&AShutdown handling›
Termination Flow
  • 1. SIGTERM sent to main process
  • 2. Pod stops accepting new traffic (removed from service)
  • 3. preStop hook runs (if defined)
  • 4. App handles SIGTERM, closes connections, saves state
  • 5. terminationGracePeriodSeconds wait (default 30s)
  • 6. If still running after grace period: SIGKILL (force kill)
Implementation
  • App catches SIGTERM signal
  • Stop accepting requests
  • Finish in-flight requests (with timeout)
  • Close database connections
  • Flush caches, save state
  • Exit cleanly
Pod Config
spec:
  terminationGracePeriodSeconds: 30  # Wait time before SIGKILL

  containers:
  - name: app
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "sleep 5"]  # Time to drain requests
Say this in interview "App must catch SIGTERM. Stop accepting traffic, finish in-flight requests, close connections. Set terminationGracePeriodSeconds to allow time (default 30s). preStop hook for additional cleanup."

Explain canary deployments and blue-green deployments

Advanced deployment strategies for safe releases. Minimize blast radius of bad deployments.

Q&ASafe rollouts›
Canary Deployment
  • Roll out to small % of traffic first (5%)
  • Monitor for errors
  • If good, gradually increase (5% → 25% → 50% → 100%)
  • If bad, rollback immediately
  • Implemented with: service mesh or Flagger
Blue-Green Deployment
  • Blue: old version (current production)
  • Green: new version (staging)
  • Run both in parallel
  • Switch traffic from blue to green (fast, atomic)
  • Rollback easy: switch back to blue
Comparison
  • Canary: gradual, detect issues early, longer deployment
  • Blue-green: atomic switch, faster, needs double resources
Say this in interview "Canary: send 5% traffic to new version, monitor, gradually increase. Blue-green: run both versions, instantly switch traffic. Canary safer for large changes, blue-green faster but needs 2x resources."

How do you implement high availability and disaster recovery for Kubernetes?

HA = no single point of failure. DR = recovery from disaster.

Q&AResilience›
HA (High Availability)
  • Multi-node cluster (3+ control plane nodes)
  • Multiple replicas per app (never 1 replica)
  • Pod anti-affinity: spread replicas across nodes
  • Node failures don't cause downtime
DR (Disaster Recovery)
  • RTO: how fast to recover (target recovery time)
  • RPO: how much data loss acceptable (recovery point)
  • Backups: Velero for cluster backups
  • Multi-region: replicate cluster to different region
  • Restore procedures: test regularly
Implementation
  • 3 control plane nodes (distributed, different zones)
  • 3+ worker nodes (distributed)
  • etcd replicated across zones
  • Persistent data: replicated storage
  • Backups to separate region/cloud
Say this in interview "HA: multiple control plane nodes, multiple replicas, spread across zones. DR: regular backups (Velero), secondary cluster, test recovery procedures. Define RTO/RPO targets."

Multi-tenancy & Tenant Isolation in Kubernetes

Isolate tenants so they can't interfere with each other. Critical for SaaS.

Q&AIsolation strategies›
Isolation Levels
  • Namespace: separate namespaces per tenant (logical)
  • RBAC: tenant ServiceAccount can only access their namespace
  • Network Policies: tenants can't reach each other
  • Resource Quotas: limit CPU/memory per tenant
  • Dedicated nodes: tenant pods on isolated nodes (strongest)
Implementation
  • 1. Create namespace per tenant: tenant-a, tenant-b
  • 2. Create ServiceAccount per tenant
  • 3. RBAC: ServiceAccount can access only its namespace
  • 4. NetworkPolicy: deny all, allow within namespace
  • 5. ResourceQuota: limit 10 CPU, 20GB RAM per tenant
Challenges
  • Control plane shared (risk if compromised)
  • etcd shared (encrypt secrets, limit access)
  • Noisy neighbor: one tenant's load affects others (use quotas)
Say this in interview "Namespace per tenant, RBAC restricts access, NetworkPolicy prevents cross-tenant traffic, ResourceQuota limits resources. Combines logical and resource isolation for security."

Persistent data needs protection. Multiple strategies depending on volume type and application.

Q&AData protection›
Backup Approaches
  • Cloud snapshots: Azure snapshots, AWS EBS snapshots (point-in-time)
  • Velero: Backup entire K8s cluster including volumes
  • App-level backups: Database dump (mysqldump, pg_dump)
  • Persistent replication: Database replicas in another region
Velero Backup
  • Backs up K8s resources AND persistent volumes
  • Can backup entire namespace or cluster
  • Restores to same or different cluster

Restore Strategy
