Problem scenarios

"The server is slow. How do you check it?"

The most common Linux question. They want to see if you follow a clear order.

ProblemFirst 60 seconds›
Check — in this order
uptime              # is load going up or down?
dmesg -T | tail     # OOM kills, disk errors
vmstat 1 5          # r, b, si/so, us/sy/id/wa
mpstat -P ALL 1     # is one core busy and others free?
pidstat 1           # which process uses the CPU
iostat -xz 1        # disk %util and await
free -m             # look at available, not free
top                 # confirm what you already found
What the numbers mean
You seeIt means
wa is highWaiting on disk. Go to iostat and find the device
sy is highToo much kernel work. Many system calls, or heavy network load
r is more than the core countToo many processes waiting for CPU. Real CPU shortage
si/so are not zeroThe server is swapping. Memory is the real problem
%util near 100Disk is full of work. Check await to see how slow
Load high, everything else normalLook for D state processes (see next topic)
Say this first "Before I log in, I check two things. Is it slow for all users or only one user? And did it start after a deployment? Many times the cause is a change, not a resource limit."
Problem scenarios

"df says the disk is full but du does not."

Asked often. The simple answer is only one of four causes.

ProblemFour causes›
Cause 1 — file deleted but still open

A program still has the file open. The name is gone, so du cannot see it. But the disk space is not free until the program closes it.

lsof +L1                      # files with no name left
lsof -nP | grep '(deleted)'
: > /proc/<pid>/fd/<n>        # empty it without a restart

This usually happens when someone runs rm on a log file instead of emptying it.

Cause 2 — no inodes left

Space is free but you cannot create a file. Too many small files.

df -i    # IUse% shows 100%
Cause 3 — files hidden under a mount

Files were written to /data before the disk was mounted there. They still use space but you cannot see them.

mount --bind / /mnt && du -sh /mnt/data
Cause 4 — reserved space

ext4 keeps 5% for root. The app sees "full" while df still shows a little space.

tune2fs -l /dev/sda1 | grep -i reserved
Problem scenarios

"Load average is 40 but the CPU is 95% idle."

ProblemProcesses waiting on disk›
The answer

Linux load counts two kinds of processes: R (running) and D (waiting for disk). So processes stuck on disk raise the load even when the CPU is free. Most other Unix systems count only running processes.

Check
ps -eo state,pid,wchan:30,cmd | awk '$1 ~ /^D/'
cat /proc/pressure/io          # real waiting time
iostat -xz 1
dmesg -T | grep -i -E 'nfs|timeout|i/o error'
Usual causes
  • Slow or failing disk — check await and kernel errors
  • NFS mount is hanging. Every process touching it gets stuck
  • Storage problem on the backend, or Azure disk throttling
  • Heavy database writes calling fsync
Careful You cannot kill a D state process, even with -9. The signal waits until the process comes back from the kernel. Fix the disk problem instead.
Problem scenarios

"A process disappeared and the app log shows nothing."

ProblemThe OOM killer›
Check
dmesg -T | grep -i -E 'killed process|out of memory'
journalctl -k --since "1 hour ago" | grep -i oom

The kernel line shows which process was killed and how much memory it used.

How the kernel picks the victim
  • oom_score goes up with memory used
  • oom_score_adj (−1000 to 1000) changes the score. −1000 means almost never killed
  • The process using the most memory is killed. This is often not the process that caused the problem
Fix
  • Set MemoryMax= in the systemd unit so that process dies alone, not its neighbour
  • Add swap on purpose. Then the server slows down instead of killing a process, and you can alert on it
  • Fix the memory leak. Adding RAM only delays the problem

Problem scenarios

"Something is using port 8080. Find it."

CommandsFind the process› 
ss -ltnp                  # listening tcp ports with process
lsof -i :8080
fuser -n tcp 8080
  • ss replaced netstat. It asks the kernel directly instead of reading /proc, so it is much faster on busy servers
  • You need root to see process names for other users
Careful If the port is busy but ss shows nothing, the socket is in a different network namespace. This is normal on a container host. Use nsenter -t <pid> -n ss -ltnp.
Problem scenarios

"A process will not die, even with kill -9."

ProblemTwo different cases›
StateWhat is happeningWhat to do
DStuck inside a kernel call, usually disk. Signals wait, they are not deliveredFix the disk problem. If not possible, reboot
ZAlready dead. It stays in the list because the parent did not collect itYou cannot kill it. Kill or fix the parent
 
ps -eo state,pid,ppid,wchan:25,cmd | grep -E '^[DZ]'
Remember A few zombies are harmless. Thousands means the parent has a bug and you will run out of PIDs. This is why a container needs a proper init like tini or --init when PID 1 is an app that does not clean up its children.
Problem scenarios

"Too many open files"

ProblemFile descriptor limit›
Check
ulimit -n                        # limit for your shell
cat /proc/<pid>/limits           # the real limit for that process
ls /proc/<pid>/fd | wc -l        # how many it has open
sysctl fs.file-nr                # whole system

Always read /proc/<pid>/limits. Your shell limit is often different.

Fix — depends how it was started
systemd serviceLimitNOFILE= in the unit, then daemon-reload and restart
Login shell/etc/security/limits.conf
Whole systemfs.file-max with sysctl
Careful — this is the real question limits.conf is applied by PAM at login. systemd services do not go through PAM. So editing that file and restarting the service does nothing.

Problem scenarios

"The app cannot resolve a hostname, but dig works."

Problemdig and the app use different paths›
The key point

dig asks the DNS server directly. An application does not. It uses NSS, which reads /etc/nsswitch.conf, checks /etc/hosts first, and then DNS. getent uses the same path as the application.

dig example.com              # DNS only
getent hosts example.com     # same path as the app

If dig works and getent fails, the problem is not DNS.

Then check
resolvectl status
cat /etc/resolv.conf          # may point to 127.0.0.53
dig @168.63.129.16 example.com   # Azure DNS
Common causes
  • A search domain is added to the name. Try a dot at the end: example.com.
  • Old entry in /etc/hosts hiding the real DNS answer
  • Private DNS zone not linked to the VNet, so the record really does not exist there
Problem scenarios

"Memory usage is high. Find the cause."

ProblemFive things to check in order›
Check
free -m                                    # look at available
ps -eo pid,rss,comm --sort=-rss | head     # biggest processes
df -h | grep tmpfs                         # tmpfs uses memory
grep -E 'Slab|SReclaimable|Dirty' /proc/meminfo
Go through these in order
  1. Is it really a problem? Look at available. If that is high, there is nothing wrong
  2. Is it file cache? Cache is reclaimable. The kernel gives it back when an app needs it
  3. Is one process growing? Compare RSS now and one hour later. Growth over time means a leak
  4. Is it kernel memory? A growing Slab value points to a driver or filesystem problem, not an app
  5. Is it tmpfs? Files written to a tmpfs mount are stored in RAM
Careful A tmpfs mount filling up looks exactly like an application using memory. Always run df -h | grep tmpfs before blaming the app.
Remember On a container host, check the memory of the cgroup, not the host. A container can be killed for going over its own limit while the host still has plenty of free memory.
Problem scenarios

"The app is slow but CPU looks fine." — steal time

ProblemThe problem is outside the VM›
Where to see it
top          # the "st" value in the CPU line
vmstat 1 5   # the "st" column
mpstat 1     # %steal
What it means

Steal time is CPU time the hypervisor took away from your VM and gave to another VM. Your own numbers look normal because the work simply never ran.

  • A noisy neighbour on the same physical host
  • A burstable VM that has used up its CPU credits
  • The host itself is oversubscribed
Say this for Azure "If steal time is more than a few percent, the problem is outside the VM. On Azure this is usually a B-series burstable VM that has used all its CPU credits. The fix is a different VM size, not tuning the application."
Shell basics

Exit status and && ||

Concept0 means success› 
command; echo $?     # 0 = success, anything else = failure

cmd1 && cmd2         # run cmd2 only if cmd1 worked
cmd1 || cmd2         # run cmd2 only if cmd1 failed
cmd1 ; cmd2          # always run both

mkdir /data && cd /data
systemctl start app || echo "start failed"
  • $? holds the result of the last command only
  • Exit code 0 is success. This is the opposite of most programming languages, where 0 is false
Careful — pipelines In cmd1 | cmd2, $? is the result of cmd2 only. If cmd1 fails, the pipeline still looks successful. Use set -o pipefail in scripts, or read ${PIPESTATUS[@]}.

Environment variables

ConceptAnd which file runs when›
Basics
VAR=value            # only in this shell
export VAR=value     # also passed to child processes
printenv | sort
echo $VAR
unset VAR
Which file is read
.bash_profileRuns for a login shell — when you SSH in
.bashrcRuns for an interactive shell — a new terminal tab
/etc/profileSame as .bash_profile but for all users

On most systems .bash_profile loads .bashrc, so it works either way.

Careful — the interview point A systemd service and a cron job do not read .bashrc or .bash_profile. Setting a variable there and restarting the service does nothing. Use Environment= in the systemd unit, or set it inside the cron script.
Processes & signals

Load average

ConceptWhat the three numbers mean›
  • Averages over the last 1, 5 and 15 minutes
  • It counts processes that are running or waiting for disk. It is not a CPU percentage
  • Compare it with nproc. Load 8 on 8 cores is full. Load 8 on 2 cores is far too much
  • The direction matters. If the 1 minute value is much higher than the 15 minute value, the problem is growing right now
Good to add /proc/pressure/cpu, io and memory show the real percentage of time processes had to wait. This is more useful than load average.

Processes & signals

ps vs top vs htop

CommandsWhich fields actually matter› 
ps aux                    # BSD style
ps -ef                    # System V style
ps -eo pid,ppid,user,%cpu,rss,stat,start,cmd --sort=-%cpu | head
  • ps gives one snapshot. top keeps updating
  • In top: press 1 for each core, M to sort by memory, P by CPU, c for the full command
  • htop is the same but easier to read and scroll
Say this "I look at RSS, not VSZ. VSZ counts memory that is only mapped and may never be used, so it looks alarming but means very little. RSS is the memory really held in RAM."

The /proc filesystem

ConceptThe kernel as files› 
# about the system
/proc/cpuinfo        # CPU model and cores
/proc/meminfo        # detailed memory
/proc/loadavg        # load and process counts
/proc/mounts         # what is mounted

/proc/<pid>/cmdline  # the full command

Users & sudo

Creating and changing users

CommandsAnd the -a trap› 
useradd -m -s /bin/bash -G docker sanjay   # -m creates the home folder
passwd sanjay

usermod -aG docker sanjay      # ADD to a group
usermod -s /sbin/nologin svc   # block login for a service account
userdel -r sanjay              # -r also removes the home folder
Careful — common mistake usermod -G docker sanjay without -a replaces all secondary groups. The user is removed from every other group. Always use -aG.
Remember A group change does not affect a session that is already open. The user must log out and log in again. This is the same reason a new docker group member cannot run Docker until they reconnect.
Users & sudo

su vs sudo, and the sudoers file

ConceptWhy sudo is preferred›
The difference
su - userBecome that user completely. Needs their password
sudo cmdRun one command as root. Needs your own password, and every use is logged

sudo is better because there is no shared root password, every action is recorded, and access can be limited to specific commands.

Rule format
sanjay ALL=(ALL) ALL
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart myapp
%devops ALL=(ALL) ALL         # % means a group

# user  host=(run as whom)  which commands
Say this "I always edit with visudo, never with a normal editor. It checks the syntax before saving. One mistake in that file can lock everybody out of root access. I also put custom rules in /etc/sudoers.d/ so a package update does not remove them."
Users & sudo

Password ageing and locking an account

Commandschage and passwd -l› 
chage -l sanjay              # show current settings
chage -M 90 sanjay           # password expires after 90 days
chage -m 7 sanjay            # cannot change again for 7 days
chage -W 14 sanjay           # warn 14 days before
chage -E 2026-12-31 sanjay   # the account itself expires

passwd -l sanjay             # lock the password
passwd -u sanjay             # unlock
Careful — the follow-up question Locking the password does not stop SSH key login. The key still works. To fully block the user, also set the shell to /sbin/nologin or expire the account with chage -E.

Files & permissions

umask

ConceptPermissions that get removed›
  • umask is the set of permissions removed when a new file is created
  • The start value is 777 for folders and 666 for files. Files never get execute permission by default
  • umask 022 gives folders 755 and files 644
  • umask 077 gives 700 and 600. Use this for anything with secrets
  • For a service, set UMask= in the systemd unit, not in .bashrc

Files & permissions

Inodes

ConceptHolds the details, not the name›
  • An inode holds the owner, permissions, timestamps, size, link count and where the data blocks are
  • It does not hold the file name. The name is stored in the folder entry that points to the inode
  • On ext4 the number of inodes is fixed when the filesystem is created. Many small files can use them all while space is still free
df -i
find /var -xdev -printf '%h\n' | sort | uniq -c | sort -rn | head

The second command finds the folder holding the most files.

Memory & storage

Reading free -m

Careful"free" is the wrong column›
  • free — really unused memory. A busy healthy server has very little. Unused RAM is wasted RAM
  • buff/cache — file cache. The kernel gives it back when needed
  • available — the number that matters. How much a new process can get without swapping
Careful Saying "only 200 MB free, we need more RAM" is wrong when available shows 12 GB. Set alerts on available, never on free.
Memory & storage

Swap & swappiness

ConceptA value from 0 to 100›
  • vm.swappiness decides how quickly the kernel moves memory to swap instead of dropping file cache. Default is 60
  • A low value (1 to 10) is better for databases and fast APIs
  • 0 does not turn swap off. It only swaps to avoid an OOM kill
  • You see swap activity as si and so in vmstat. If they stay above zero, there is a real problem
Remember Kubernetes used to refuse to start when swap was on, because swap breaks the memory limits and eviction logic. It is now optional, but swap is still turned off on AKS.

systemd basics

CommandsDaily service management› 
systemctl status nginx
systemctl enable --now nginx      # enable and start
systemctl daemon-reload           # after ANY unit file change
systemctl list-units --failed
systemctl cat nginx               # the unit plus any overrides

Careful — two common mistakes Do not edit the file in /usr/lib/systemd/system/. A package update will replace it. Use systemctl edit instead. And always run daemon-reload, or your change does nothing and there is no error.

Restart=on-failure or always, with RestartSec=
LimitNOFILE=The open file limit that actually works for services
MemoryMax=Memory cap. The service is killed alone, not a neighbour
After= / Requires=Order vs need. After alone does not start the other unit
systemd & boot

journalctl

CommandsFinding the right log line› 
journalctl -u nginx -f
journalctl -u nginx --since "10 min ago"
journalctl -p err -b                # errors since this boot
journalctl -b -1                    # the boot before this one
journalctl -k                       # kernel messages

Remember On some systems the journal is stored in memory and is lost on reboot. If -b -1 shows nothing after a crash, that is why. Set Storage=persistent in journald.conf.
systemd & boot

Boot sequence

ConceptPower on to login›
  1. Firmware (UEFI or BIOS) — hardware check, then find the boot disk
  2. Bootloader (GRUB2) — loads the kernel and initramfs
  3. Kernel — starts and uses initramfs as a temporary root
  4. initramfs — loads the drivers needed to see the real disk, then switches to it
  5. PID 1 (systemd) — starts services until it reaches default.target
Common follow-up "Root password lost" — edit the GRUB entry, add rd.break or init=/bin/bash, mount root as read-write, change the password. On SELinux systems also run touch /.autorelabel.

Docker

Basics

Image, container, layer

A layer is a file change from one Dockerfile instruction. An image is a stack of layers plus metadata. A container is an image with a writable layer on top, running as an isolated process. When you run 50 containers from one image, they share the same layers—that's copy-on-write efficiency.

ConceptThree words people mix up›
LayerThe file changes made by one instruction. Read-only, and shared by every image that uses it
ImageA stack of layers plus settings — env, entrypoint, cmd, user, ports
ContainerAn image plus a small writable layer, running as a process with namespaces and cgroups
 
docker history <image>
docker image inspect <image>
docker diff <container>          # what changed in the writable layer
Say this "Fifty containers from one image use one copy of the image plus fifty small writable layers. That is copy-on-write. The writable layer is deleted with the container, so anything I need to keep must go in a volume."
Basics

Docker architecture

Docker has a client-daemon architecture. The client sends commands to the daemon, which manages images, containers, and volumes. When you docker run, the daemon pulls the image from a registry (Docker Hub, ACR, ECR), creates a container from it, and runs it. Understanding this split is key to troubleshooting network and permission issues.

ConceptCLI → dockerd → containerd → shim → runc›
docker CLIOnly a client. Talks to the daemon over /var/run/docker.sock
dockerdBuild, networks, volumes, the API. Passes container work down
containerdPulls images and manages the container life cycle
containerd-shimOne per container. Stays alive as the parent, so containerd can restart without killing containers
runcCreates the namespaces and cgroups, starts the process, then exits
Good detail to add runc does not keep running. It sets things up and exits. The shim is what stays. This is why you can restart the Docker daemon without stopping running containers when live-restore is on.
Basics

containerd, CRI-O and the dockershim removal

ConceptWhy Kubernetes removed Docker›
The three things
  • containerd — speaks Kubernetes CRI directly. AKS uses this
  • CRI-O — a small runtime built only for Kubernetes. Used by OpenShift
  • Docker Engine — a full developer tool (build, compose, CLI) built on top of containerd. It never spoke CRI
What happened

kubelet needed a translator to convert CRI calls into Docker calls. That translator was removed in Kubernetes 1.24. AKS had already moved to containerd from version 1.19.

What it changed in practice
  • Images are not affected. They follow the OCI standard, so images built with docker build still run
  • docker ps on a node no longer shows pods. Use crictl ps and crictl logs
  • Anything that mounted docker.sock on the node, or read Docker's log files, had to be changed
Say this "Kubernetes removed a translation layer, not container support. Docker builds OCI images and containerd runs them. My images did not change. Only the tools on the node changed."
Dockerfile

CMD vs ENTRYPOINT

CarefulAnd why shell form breaks shutdown›
The difference
  • ENTRYPOINT is the program to run. Anything you type after the image name is added to it
  • CMD is the default arguments. Anything you type after the image name replaces it
  • To change ENTRYPOINT you must use the --entrypoint flag
ENTRYPOINT ["/app/server"]
CMD ["--port=8080"]

docker run img              # /app/server --port=8080
docker run img --port=9090  # /app/server --port=9090
Exec form vs shell form
Exec form ["cmd","arg"]No shell. Your program is PID 1 and receives signals
Shell form cmd argRuns inside /bin/sh -c. sh becomes PID 1 and does not pass SIGTERM to your program
Careful — what goes wrong With shell form, SIGTERM goes to sh. sh ignores it, so your app never shuts down properly. docker stop waits 10 seconds and then kills it. In Kubernetes it waits 30 seconds and then kills it, and open connections are dropped. Always use exec form.
Remember — asked very often In Kubernetes, command: replaces ENTRYPOINT and args: replaces CMD. The names do not match, and interviewers like to test this.
Dockerfile

COPY vs ADD

ConceptUse COPY›
  • COPY — copies local files and folders only. It does nothing extra, and that is why it is better
  • ADD — also unpacks local tar files and can download from a URL

Use COPY every time. Use ADD only when you really want a tar file unpacked.

COPY --chown=app:app ./src /app     # no extra RUN chown layer
COPY --from=builder /out/bin /usr/local/bin/

# better than ADD https://... :
RUN curl -fsSL https://x/f.tgz -o /tmp/f.tgz \
 && echo "<sha256>  /tmp/f.tgz" | sha256sum -c - \
 && tar -xz -C /opt -f /tmp/f.tgz \
 && rm /tmp/f.tgz
Why the RUN version is better ADD with a URL cannot check the file is correct, does not handle login, and leaves the downloaded file inside the layer. The RUN version downloads, checks and deletes in one layer, so nothing is left behind.

Multi-stage builds

PatternBuild big, ship small› 
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download                 # cached until deps change

  • Only the last stage is shipped. The compiler, the source code and any build secrets stay behind
  • --target build stops at a named stage. Useful for a test stage in CI
  • Security improves as much as size. No shell and no package manager means less for an attacker to use
Say this "A Go service goes from about 900 MB on the full golang image to under 20 MB on distroless. It is smaller and it also has a much smaller attack surface."
Dockerfile

Making images smaller

PatternLayers only add, never remove›
Careful — the main point Deleting a file in a later layer does not make the image smaller. The data is still inside the earlier layer. You must install and clean up in the same RUN command. 
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*
The rest of the list
  • Pick a small base: distroless, then alpine, then slim, then full
  • Multi-stage build — usually the biggest saving
  • .dockerignore — keeps .git, node_modules and build output out of the build. Also makes builds faster
  • Order the instructions — put things that change rarely first. Copy the dependency file before the source code, so a code change does not rebuild the dependencies
  • docker history --no-trunc shows which layer is large
Good to add Alpine uses musl instead of glibc. Some programs built for glibc will not run, and some workloads have DNS problems on it. Distroless keeps glibc and is usually the safer small base.
Images & registry

Tags vs digests

CarefulA tag can change, a digest cannot›
  • A tag is only a label. It can be moved to different content at any time
  • A digest (sha256:…) is made from the content itself, so it never changes
  • :latest is just a default tag name. It does not mean newest
image: myacr.azurecr.io/app@sha256:9f2c…   # fixed, repeatable
docker inspect --format='{{index .RepoDigests 0}}' app:1.4.2
Remember — imagePullPolicy Kubernetes uses Always when the tag is latest, and IfNotPresent for any other tag. So with a tag like :prod, the node keeps the old image and your redeploy quietly runs old code.
Careful — the bug this causes Staging and production both use :v1.4, but the tag was rebuilt in between. Same tag, different content. This causes hours of "but it works in staging". Use a version tag in CI and pin production by digest.

Logging & rotation

CarefulThe default has no size limit›
What happens

The default json-file driver writes logs under /var/lib/docker/containers/ with no rotation. One noisy container fills the host disk, and then every container on that host starts failing.

Fix it for the whole host
// /etc/docker/daemon.json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}

This applies to new containers only. Existing ones keep their old setting.

Points to make
  • Apps should write to stdout and stderr, not to files inside the container. Let the platform collect and rotate
  • docker logs works only with json-file, local and journald. If you switch to fluentd, the command shows nothing
  • On AKS this is different. containerd writes to /var/log/pods, kubelet rotates the files, and Azure Monitor or Fluent Bit reads them

"DNS does not work inside the container."

ProblemThree different causes›
Check
docker exec <c> cat /etc/resolv.conf
docker run --rm --network appnet busybox nslookup db

Cause 1 — wrong network

Container names only work on a network you created yourself. On the default bridge, names never resolve.

Cause 2 — the host uses a local resolver

If the host /etc/resolv.conf points to 127.0.0.53, Docker cannot pass that to the container, because loopback inside the container is different. Docker uses a public DNS server instead, which fails on any network that blocks external DNS.

// /etc/docker/daemon.json
{ "dns": ["168.63.129.16"] }     // Azure DNS
Cause 3 — MTU mismatch

Small lookups work, large answers and TLS get stuck. Common on VPN or cloud networks with a smaller MTU. Set "mtu" in daemon.json to match the host.

Remember Kubernetes has the same class of problem with different parts: CoreDNS instead of Docker's DNS, and ndots: 5 which causes several failed lookups before the correct one. A dot at the end of the name skips them.

Exit codes

Exit code 137 tells me the kernel killed the process, but not why. It could be OOMKilled, a failed liveness probe, or node eviction. I always check lastState.terminated.reason in kubectl describe to see the actual cause. Exit code 1 means app error—read the logs. Exit code 143 is normal during a rollout (SIGTERM).

ConceptThe code narrows it down, it does not give the cause›
CodeMeaning
0Finished normally, but the container should keep running. Usually a script that ended or a program that went to the background
1Application error. Read the logs
126Found but cannot run. Missing +x
127Command not found. Wrong path, or missing from a small base image
137Killed with SIGKILL. Usually out of memory, but also a failed liveness probe or eviction
143Stopped with SIGTERM. Normal during a rollout
Say this "137 tells me the kernel or kubelet killed it, but not why. I check lastState.terminated.reason to see if it was OOMKilled or a probe failure."
Pod failure states

CrashLoopBackOff

When a pod is in CrashLoopBackOff, the container keeps crashing and Kubernetes keeps restarting it with exponential backoff. I start by checking kubectl logs to see what the app is complaining about. If logs are empty, I check the events (kubectl describe pod) to see if it's a startup probe failure or resource limits. Then I look at the readiness/liveness probe configuration—sometimes the probes are misconfigured and kill healthy containers.

FailStarts, exits, restarts, waits longer›
Check
kubectl logs <pod> --previous   # logs from the crashed container
kubectl describe pod <pod>      # events, exit code, restart count

--previous is the important part. Without it you read a container that just started.

Causes
  • Out of memory — the limit is lower than what the app really needs
  • Missing or wrong env var, Secret or ConfigMap key
  • Liveness probe runs before the app has finished starting
  • Wrong CMD or ENTRYPOINT, or the program does not stay in the foreground
  • A service it depends on is not ready
Fix
  • Raise the memory limit, or fix the leak
  • Add a startupProbe so the liveness probe waits for slow starts
  • Use an initContainer to wait for dependencies instead of crashing
  • Check the ConfigMap and Secret exist in the same namespace

"How does Kubernetes work? Explain the control plane."

ConceptThe three layers›
Control plane (API server & friends)
  • API Server: Stores and retrieves everything. Every kubectl command talks to it
  • etcd: Key-value store. Holds all cluster state. If it breaks, cluster is gone
  • Controller Manager: Runs reconciliation loops. Wants state = desired state
  • Scheduler: Assigns pods to nodes based on resources and constraints
Worker nodes (kubelet & friends)
  • kubelet: Agent on each node. Reports node status, runs pods
  • Container runtime: Docker, containerd, CRI-O. Starts and stops containers
  • kube-proxy: Manages iptables rules for Services and networking
The reconciliation loop
User creates a Deployment with 3 replicas
  ↓
API Server stores it in etcd
  ↓
Deployment controller sees new resource
  ↓
Controller creates 3 ReplicaSets
  ↓
ReplicaSet controller creates 3 Pods
  ↓
Scheduler assigns each Pod to a node
  ↓
kubelet on each node pulls image and starts container
  ↓
Pod is running!

"What are controllers? How do they work?"

ConceptControllers == reconciliation›
Core idea

A controller is a loop that watches resources and tries to make current state = desired state.

while true:
  current = get_resource_state()
  desired = get_spec()
  if current != desired:
    take_action_to_fix()  # create, update, delete
Examples
ControllerWatchesWhat it does
DeploymentDeploymentsCreates ReplicaSets when spec changes
ReplicaSetReplicaSetsCreates/deletes Pods to match replicas count
StatefulSetStatefulSetsManages ordered pods with stable names
NodeNodesMarks nodes NotReady if unhealthy
Say this first "Controllers are just loops. They read the spec, check the current state, and take actions to match them. This is how Kubernetes achieves self-healing."

"How does a Deployment roll out new versions? How do rollbacks work?"

ConceptRollingUpdate strategy›
Rolling update (default)
Old: 3 replicas running
  ↓
Change image in spec
  ↓
Controller gradually replaces pods:
  - Start 1 new pod (4 total now)
  - Wait for it to be ready
  - Kill 1 old pod (back to 3)
  - Repeat until all are new
  ↓
New: 3 new replicas

If something goes wrong, bad pods are not healthy
and the controller stops rolling out.
Monitor and rollback
kubectl rollout status deployment/my-app  # watch progress
kubectl rollout history deployment/my-app  # past revisions
kubectl rollout undo deployment/my-app      # go back
kubectl rollout undo deployment/my-app --to-revision=2
Control the speed
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1           # max extra pods during update
      maxUnavailable: 0     # pods that can be down
Say this first "By default, Kubernetes slowly replaces pods. Healthy checks prevent bad versions from spreading. You can rollback instantly if needed."

"When should you use StatefulSets instead of Deployments?"

ConceptStateful vs stateless›
Deployments (stateless)
  • Pods have no identity. Any pod can replace any other
  • Order doesn't matter
  • Good for: web servers, APIs, microservices
StatefulSets (stateful)
  • Each pod has a stable name (e.g., mysql-0, mysql-1, mysql-2)
  • Each pod gets its own persistent volume
  • Pods are created and deleted in order
  • Good for: databases, message queues, cluster software
Why this matters
Database needs:
  - Stable network identity (for replication)
  - Own persistent storage (different data per pod)
  - Ordered startup (start master before replicas)

Deployment can't guarantee this.
StatefulSet does.

"How do you restrict network traffic between pods?"

ConceptNetworkPolicy for security›
By default: all traffic allowed

Any pod can talk to any other pod. Good for development, bad for security.

# Default deny all incoming
kind: NetworkPolicy
metadata:
  name: deny-all-ingress
spec:
  podSelector: {}
  policyTypes:
  - Ingress

# Then allow only from specific pods
---
kind: NetworkPolicy
metadata:
  name: allow-from-frontend
spec:
  podSelector:
    matchLabels:
      tier: backend
  policyTypes:
  - Ingress

  - from:

      port: 8080

"What is Pod Security? What's the difference between PSP and Pod Security Standards?"

  • You set a PSP and bind it with RBAC
  • Pods that don't match the PSP are rejected

  • No privileged containers
  • Root filesystem must be read-only
  • No cap_add (all capabilities dropped)
  • No SELinux type unrestricted

"How does persistent storage work? StorageClass, PVC, PV?"

ConceptThe three layers›
PersistentVolume (PV) — the storage
  • A piece of storage in the cluster (AWS EBS, Azure Disk, NFS share)
  • Can be created manually or dynamically
  • Has a size, access mode (ReadWriteOnce, ReadOnlyMany, ReadWriteMany)
PersistentVolumeClaim (PVC) — the request
  • A pod says "I need storage of 10GB"
  • PVC finds a PV that matches, or triggers dynamic provisioning
  • Pod mounts the PVC as a volume
kind: PersistentVolumeClaim
metadata:
  name: my-data
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 10Gi
StorageClass — the provisioner
  • Tells Kubernetes how to create PVs dynamically
  • References a cloud provider's storage API (AWS EBS, Azure, GCP)
  • When a PVC is created, the controller provisions a real disk
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  iops: 3000
The flow
Pod requests PVC
  ↓
PVC looks for matching PV or uses StorageClass
  ↓
StorageClass tells cloud provider to create disk
  ↓
PV is created, PVC is Bound
  ↓
Pod can mount the volume
Common issues
  • PVC stuck in Pending: StorageClass doesn't exist or has no provisioner
  • Pod can't mount: PVC is not Bound, or access mode mismatch
  • Disk won't detach: pod in Terminating, volume still has mount locks

Networking & traffic

"What is a service mesh? When would you use Istio?"

ConceptPod-to-pod networking layer›
Problem: pod-to-pod communication
  • Each pod talks to many others. How do you handle retries, timeouts, failures?
  • How do you add observability (traces, metrics) without modifying app code?
  • How do you enforce security policies (which pods can talk to which)?
  • How do you do gradual rollouts (send 10% to new version, 90% to old)?
Solution: service mesh
  • Deploys a "sidecar" proxy (Envoy) in each pod
  • All network traffic goes through the sidecar
  • Mesh controller manages routing, retries, security, observability
  • Apps don't need to know about the mesh
Pod: [App Container | Envoy Sidecar]
                    ↑
                    Mesh Controller
                    (Istiod)

Every pod has Envoy. Envoy intercepts all traffic.
Istio: the most popular service mesh
  • Istiod: Control plane. Manages Envoy sidecars
  • Envoy: Sidecar proxy in each pod
  • VirtualService: Define how traffic flows (e.g., "send 10% to v2")
  • DestinationRule: Define how to reach a service (load balancing, circuit breaking)
  • PeerAuthentication: Enforce mTLS between pods
Example: canary deployment
# 90% traffic to v1, 10% to v2 (new version)

metadata:
  name: my-app
spec:
  hosts:
  - my-app
  http:
  - match:
    - headers:
        user-id:
          exact: "canary-user"
    route:
    - destination:
        host: my-app
        subset: v2
  - route:
    - destination:
        host: my-app
        subset: v1
      weight: 90
    - destination:
        host: my-app
        subset: v2
      weight: 10

3. Monitor for 10 minutes

"What's the difference between monitoring and observability?"

Two related but different concepts. Monitoring tells you what happened. Observability lets you figure out why.

ConceptKnow the difference›
Monitoring (reactive)
  • Check if system is working: "Is the server up? Is CPU high? Are requests coming in?"
  • Predefined metrics and alerts
  • Example: CPU > 80% → send alert
  • Answers: What is the current state?
Observability (proactive)
  • Understand system internals: "Why is CPU high? Which query is slow? Where did the request fail?"
  • Three pillars: metrics, logs, traces
  • Correlate data: find the root cause of issues
  • Answers: Why did something happen? What went wrong?

Alerts on known problemsHelps debug unknown problems
Uses dashboardsUses logs, traces, and correlation
"Server is down""Server is down because disk is full because log rotation failed"

"How do you optimize monitoring cost?"

CostObservability without breaking budget›
Metrics cost optimization
  • Reduce cardinality: Don't put user ID in metric (1M users = 1M series). Aggregate instead.
  • Sample: Record 1 in 10 traces, not all. Use 10% sampling for high-volume.
  • Downsample: Keep 1-min resolution for 24h, 5-min for 30 days, 1-day for 1 year
  • Delete old metrics: Retention policy: keep 15 days, delete older
Logs cost optimization
  • Sample: Log only 10% of requests (not all)
  • Filter: Don't log debug level in production (only WARN/ERROR)
  • Compression: Logs compress well (5:1 ratio), save space
  • Retention: Keep detailed logs 7 days, archived 30 days
Traces cost optimization
  • Trace sampling: 1% of traces (10,000 requests/sec → 100 traces/sec)
  • Head sampling: Sample at entry point (browser), don't trace whole request if first span rejected
  • Tail sampling: Sample based on result (only sample errors, ignore successes)

"What is the Terraform state file? Why is it important?"

What is state?

  • Contains sensitive data (passwords, private keys)

- Their IDs or names
- What properties they have
- Whether they need updating

Interview Questions

Important Terraform Interview Questions

These are the questions I expect to answer in a Terraform interview. They test whether I understand state management, module design, remote operations, and real-world pitfalls. I answer confidently and with examples from my experience.

Q&ACore concepts & design decisions›
Q1: "Why does Terraform need a state file? Why not just read from AWS/Azure?"
  • A: Terraform state tracks resources it created and their current configuration. Without it, Terraform wouldn't know: (a) which resources it owns, (b) if a resource changed outside Terraform (drift), (c) how to map resource names in code to actual IDs in AWS. Reading live from cloud each time would be slow and error-prone.
  • Key point: State is the source of truth for Terraform, not the cloud. That's why state corruption is dangerous.
Q2: "State file contains secrets in plain text. How do you secure it?"
  • A: I never store state locally. I use remote state backends: Terraform Cloud, S3 with encryption at rest, Azure Blob Storage with encryption. For secrets specifically (passwords, API keys), I use aws_secretsmanager or azure_key_vault to store them, and reference them from Terraform using data sources. Never hardcode secrets.
  • Example: data.aws_secretsmanager_secret.db_password → reference in resource
Q3: "You're in production and someone does 'terraform destroy' by accident. What do you do?"
  • A: First, stay calm. Stop the destroy immediately (Ctrl+C if it's still running). Check the state file—did it actually destroy? Use terraform state show to see what's still there. If resources are gone, restore from backups and reimport them: terraform import azurerm_vm.prod /subscription/id. In the future: use -lock in production, require approval processes, and add protection: terraform state lock manually.
  • Prevention: Use workspaces or separate state files for prod. CI/CD approval gates. Consider terraform policies to prevent destroy without review.
Q4: "How do you handle state drift (resources changed outside Terraform)?"
  • A: terraform refresh re-reads actual state from cloud and updates state file. terraform plan will show the drift. Then I decide: (a) reimport the change into state, or (b) apply Terraform to overwrite it back to desired state. If the drift is intentional, I update the Terraform code to match reality.
  • Prevention: Use RBAC to prevent manual changes. Policy: "All infrastructure changes go through Terraform." Monitor for drift with policy as code (Sentinel in Terraform Cloud).
Q5: "Your team of 5 is all running 'terraform apply' simultaneously. What happens?"
  • A: Disaster. State locking prevents this. Remote backends (S3 with DynamoDB, Terraform Cloud) have built-in locking. When one person runs apply, the state is locked for others. If I try to apply while locked, I wait (or see "lock acquired by..."). With local state, no locking—bad idea for teams.
  • Best practice: Remote state backend is mandatory for team work. Use terraform lock explicitly for manual operations.
Q6: "How do you structure Terraform for multiple environments (dev, staging, prod)?"
  • A: I use one of two patterns: (1) Workspaces: terraform workspace select prod → different state file per workspace, or (2) Directories: environments/dev/, environments/prod/ with separate tfvars files. I prefer directories because it's clearer and allows different apply/destroy policies per environment.
  • File structure: 
    environments/
  ├─ dev/
  │  ├─ main.tf (references modules/)
  │  ├─ terraform.tfvars (dev vars)
  │  └─ backend.tf (dev state)
  └─ prod/
     ├─ main.tf
     ├─ terraform.tfvars (prod vars)
     └─ backend.tf (prod state)
modules/
  ├─ networking/
  ├─ compute/
  └─ database/
Q7: "What's the difference between terraform apply and terraform refresh?"
  • A: refresh just reads actual state from cloud and updates state file—no changes made. apply shows a plan of what will change, and applies it. refresh is read-only, apply is read-write. Use refresh when you suspect drift but don't want to make changes yet.
Q8: "How do you avoid re-creating resources when you rename them in code?"
  • A: Use terraform state mv. If I rename resource "old_name" to "new_name" in code, Terraform sees it as destroy old + create new. To avoid downtime: terraform state mv azurerm_vm.old_name azurerm_vm.new_name → tells state the resource was renamed, not deleted. Then plan will show no changes.
Q9: "Your terraform apply fails halfway through. Resources are partially created. What do you do?"
  • A: Check state to see what was created. Partial creates can happen due to network errors or API limits. Options: (1) fix the error and rerun apply—Terraform is idempotent, so it will skip completed resources and continue. (2) Manually delete partial resources and retry. (3) Use terraform taint to mark a resource for re-creation.
  • Idempotency: One of Terraform's greatest features—running apply twice is safe.
Q10: "How do you test Terraform code before applying to production?"
  • A: (1) terraform plan in staging environment with same code/config. Review the plan carefully. (2) Unit tests with Terratest or terraform test (beta). (3) Lint with tflint to catch syntax and best practice issues. (4) CI/CD pipeline: plan automatically on PR, require approval before apply. (5) terraform validate to check syntax.
  • Workflow: Commit → CI runs validate + plan + lint → human reviews plan → approve → apply
Say this in interview "State is Terraform's source of truth—without it, Terraform is blind. State should always be remote, encrypted, and locked for team work. I structure code with separate state files per environment and use modules to avoid duplication. Idempotency is key: terraform apply is safe to run multiple times. For production, I use CI/CD to plan and require manual approval before apply."

Azure VNet Connectivity (Virtual Network)

When I need to connect VNets, I first consider how many VNets we have. For two or three VNets, VNet peering is simple—direct, low latency, free. But it's not transitive, so if I have many VNets, I use hub-and-spoke with a hub VNet and user-defined routes. For hybrid on-premises connectivity, I use ExpressRoute—it's expensive but gives us dedicated bandwidth and private connectivity, which is critical for compliance.

AzureNetwork architecture patterns›
1. VNet Peering (Direct Connection)
  • Connects two VNets (same or different regions)
  • Low latency, high bandwidth, no extra cost
  • ⚠️ NOT transitive: A↔B, B↔C ≠ A↔C
  • Use: 2–3 VNets, simple regional connectivity
2. Hub-and-Spoke (Best for Many VNets)
  • Central Hub VNet + multiple Spoke VNets
  • Spokes peer only with Hub, not each other
  • Hub hosts: Firewall, Gateway, DNS, NAT
  • Use: 3+ VNets, shared resources, centralized control
3. VPN Gateway (Hybrid Connectivity)
  • Site-to-Site (S2S): On-prem ↔ Azure over IPSec
  • Point-to-Site (P2S): Individual client VPN
  • Encrypted, resilient, multiple connections
  • Higher latency & cost than peering
4. ExpressRoute (Premium Hybrid)
  • Dedicated private connection from on-prem to Azure
  • High bandwidth, low latency, consistent performance
  • No internet traversal (more secure)
  • Premium cost, requires ISP partnership
5. Azure Virtual WAN (Enterprise Scale)
  • Managed networking for branch-to-branch connectivity
  • Automated "Virtual Hub" (no VM management)
  • Any-to-any connectivity: branches, VNets, remote users
  • Built-in: VPN, ExpressRoute, Point-to-Site
  • Standard: Full features | Basic: VPN only
  • Use: 100s of sites, large enterprises
6. Azure Firewall (Central Security)
  • Place in Hub/vWAN Hub for centralized threat protection
  • Inspects all inter-VNet & branch traffic
  • Enforces policies, logs all flows, DDoS protection
Subnet Design
  • GatewaySubnet (VPN/ER) | AzureFirewallSubnet
  • AzureBastionSubnet | App | Data | Mgmt
  • NSG at subnet + NIC level
  • Private Endpoints for PaaS security

AWS VPC Connectivity (Virtual Private Cloud)

AWS has VPC Peering like Azure VNet peering, but for complex multi-VPC setups, I use Transit Gateway—it's like a hub, and all VPCs attach to it. The advantage over hub-and-spoke is that traffic doesn't route through a central VM; Transit Gateway is a managed service. For on-premises, I use AWS Direct Connect instead of ExpressRoute. It's the same concept—dedicated private connection, but AWS manages it differently and billing is also different.

AWSNetwork architecture patterns›
1. VPC Peering (Direct Connection)
  • Connects two VPCs (same or different regions/accounts)
  • Low latency, no internet traversal
  • ⚠️ NOT transitive: A↔B, B↔C ≠ A↔C
  • Use: Few VPCs, simple connectivity
2. Transit Gateway (Best for Many VPCs)
  • Central hub for VPC-to-VPC, on-prem, and VPN connections
  • Transitive peering supported (A↔TGW↔B = A↔B) ✓
  • Attachment-based: VPC, VPN, Direct Connect
  • Route tables per attachment for control
  • Use: 3+ VPCs, hybrid cloud, multi-account
3. VPN Connection (Hybrid Connectivity)
  • Site-to-Site (S2S): On-prem ↔ AWS over IPSec
  • Virtual Private Gateway (Customer Gateway setup required)
  • Encrypted, multiple connections, failover support
4. Direct Connect (Premium Hybrid)
  • Dedicated 1/10/100 Gbps connection from on-prem
  • Low latency, consistent performance, more secure
  • Higher cost, setup takes weeks
5. Networking Best Practices
  • Security Groups: stateful firewall at instance level
  • NACLs: stateless firewall at subnet level (explicit ephemeral ports)
  • Route Tables: direct traffic, UDR forces through Firewall
  • Private Endpoints: PaaS gets private IP (S3, DynamoDB, SNS)
  • AWS PrivateLink: service-to-service private connectivity
6. Firewall & WAF
  • AWS Network Firewall: VPC-level threat protection
  • WAF: Application-level (ALB, CloudFront, API Gateway)

Reliability & Cost

"High Availability & Disaster Recovery"

Before I design any HA/DR strategy, I always ask: what's the RTO and RPO? If we can tolerate an hour of downtime and 1 hour of data loss, we backup to a secondary region asynchronously. If we need 5-minute RTO and zero data loss, we deploy multi-AZ with synchronous replication—but that costs more. For databases, I use read replicas in a secondary AZ for failover, and enable automated backups with point-in-time restore. The design follows the business requirement, not the other way around.

ReliabilityRTO/RPO first›
Define First: RTO & RPO
  • RTO (Recovery Time Objective): How long to recover? (e.g., 4 hours)
  • RPO (Recovery Point Objective): How much data loss acceptable? (e.g., 1 hour)

"Message Queues & Event Streaming: Kafka vs Azure vs AWS"

Kafka is a streaming platform—data is ordered within a partition, and consumers form groups to share partitions. We use Kafka when we need message replay, topic retention, or complex processing like joins. Azure Service Bus and Event Hubs are simpler—they're transient message queues. SQS in AWS is even simpler—fire-and-forget, no ordering guarantee. The choice depends on whether we need ordering, replay capability, and the complexity of downstream processing.

MessagingDecoupling, scalability, reliability›
Apache Kafka (Open Source)
  • What: Distributed event streaming platform (not just a queue)
  • Architecture: Brokers (clusters) + Topics (channels) + Partitions (parallel)
  • Partitioning: Each partition = independent log, enables parallelism
  • Retention: Keep messages for X days (replay capability)
  • Consumer Groups: Multiple apps read same topic independently
  • Use: High-throughput event streaming, log aggregation, real-time analytics
  • Deployment: Self-hosted (Kubernetes + StatefulSet) or managed (Confluent)
Azure Options
  • Azure Service Bus: Queues + Topics (pub/sub), FIFO, dead-letter
  • Azure Event Hubs: Kafka-compatible, managed, high throughput (1M events/sec)
  • Azure Queue Storage: Simple, cheap, low-throughput (<2K msgs/sec)
  • Event Grid: Event routing, serverless, ~100 different event sources
AWS Options
  • Amazon SQS: Fully managed queues (Standard + FIFO), dead-letter, per-message delay
  • Amazon SNS: Pub/sub messaging, fan-out, message filtering
  • Amazon Kinesis: Kafka competitor, high throughput, sharding by partition key
  • Amazon MSK (Managed Streaming Kafka): Managed Kafka on AWS, multi-AZ
  • EventBridge: Event routing, serverless, 200+ event sources

"Database Replication & High Availability"

I choose between sync and async replication based on consistency needs. Sync replication guarantees all replicas are updated before acknowledging the write—slower but strong consistency. Async is faster but there's a small window where reads might see stale data. For scaling, I add read replicas in a secondary AZ for failover. I always enable automated backups with point-in-time restore. And I use connection pooling to prevent the app from exhausting database connections under load.

DatabasesReliability & scaling›
Replication Types
  • Synchronous: Write acknowledged only after replica receives (zero data loss, higher latency)
  • Asynchronous: Write acknowledged immediately (lower latency, possible data loss)
  • Semi-Synchronous: At least one replica must ack (balance)
Azure Database HA
  • SQL Database: Built-in geo-replication (read replicas) + failover groups (automatic failover)
  • MySQL/PostgreSQL: Read replicas across regions, zone-redundancy
  • Cosmos DB: Multi-region writes (active-active) by default, automatic conflict resolution
  • Multi-AZ failover: Synchronous replica in different AZ, auto-failover (<30 sec)
AWS Database HA
  • RDS Multi-AZ: Standby replica in different AZ, synchronous, automatic failover
  • RDS Read Replicas: Async copies (same region or cross-region), for read scaling
  • DynamoDB Global Tables: Multi-region active-active, eventual consistency
  • Aurora: AWS-optimized MySQL/PostgreSQL, auto-scaling replicas, 15 low-latency read replicas
Backup Strategies
  • Automated backups: Daily snapshots, retention (7-35 days)
  • Point-in-time restore (PITR): Restore to any second within retention window
  • Cross-region backups: For DR, copy snapshots to different region
  • Manual snapshots: Before major changes (long-term retention)
  • Backup & Restore time: Depends on DB size (hours for 1TB+) → factor into RTO
Connection Pooling & Performance
  • Connection pooling: PgBouncer (PostgreSQL), ProxySQL (MySQL), reduce connection overhead
  • Read replicas for scaling: Direct read traffic to replicas, write to primary
  • Caching layer: Redis for query cache, session store
  • Query optimization: Index missing columns, analyze slow query logs

"Service Mesh: Istio & Linkerd"

A service mesh sits between microservices and handles communication—mutual TLS for encryption, automatic retries, circuit breakers to prevent cascading failures, and traffic splitting for gradual rollouts. Istio is feature-rich but complex; Linkerd is lightweight and easier to operate. But I only recommend a service mesh if we have many services and need these features. For a small team or a few services, it adds complexity without benefit. The operational overhead is real—debugging becomes harder when the mesh is in the middle.

NetworkingPod-to-pod communication control›
What is a Service Mesh?

  • Simpler than Istio: Built for Kubernetes, not trying to be generic
  • mTLS by default: Automatic, zero-config

  • Observability: Traces & metrics without instrumentation

  • Team still learning Kubernetes → adds complexity
  • Strict latency requirements (<100µs) → Envoy adds overhead

"Multi-tenancy & Tenant Isolation"

When designing multi-tenant systems, I consider three isolation levels. Namespace isolation within a cluster is cheapest but has noisy neighbor risk—one tenant's spike affects others. Database per tenant is moderate cost and reduces noisy neighbor risk. Cluster per tenant is expensive but provides strong isolation, which is critical for tier-1 customers or regulated workloads. Regardless of the level, I always enforce RBAC so tenants can't access other tenants' resources, use network policies to prevent cross-tenant traffic, and implement row-level security in the database so queries can't return other tenants' data even if there's a code bug.

ArchitectureIsolation strategies & tenant management›
What is Multi-tenancy?
  • Single app serves multiple customers (tenants) with logical/physical separation
  • Cost-effective: share infrastructure, but keep data isolated
  • Compliance: regulatory isolation (HIPAA, PCI, GDPR)
  • Isolation levels: namespace-level, database-level, cluster-level, or hybrid
Azure Approaches
  • Namespace Isolation (AKS):
    • Each tenant = separate namespace in same cluster
    • RBAC: tenant-specific roles, no cross-tenant access
    • Network Policy: deny-all by default, allow only intra-tenant traffic
    • Resource Quotas: limit CPU/memory per tenant
    • Cost: cheap, but noisy neighbor risk (one tenant CPU spike affects others)
  • Cluster Isolation:
    • Each tenant = separate AKS cluster
    • Stronger isolation, but higher cost
    • Use for: tier-1 customers, regulated workloads
  • Database Isolation:
    • Shared cluster, shared app, separate databases per tenant
    • Azure SQL: logical databases, separate connection strings
    • Cost: moderate, schema is shared, data is isolated
  • Schema Isolation:
    • Single database, separate schema per tenant
    • Cheapest, but complex to manage (backup, restore, schema migrations)
AWS Approaches
  • Pod/Namespace Isolation (EKS):
    • Each tenant = namespace in EKS cluster
    • RBAC via IAM roles for service accounts (IRSA)
    • Network Policy: Calico for tenant segregation
    • Resource quotas: Karpenter for per-tenant cost tracking
  • RDS Multi-tenant:
    • Aurora PostgreSQL: logical databases or schemas
    • Row-level security (RLS): tenant_id column + policy
    • Cost-effective: single database, tenant isolation in code
  • DynamoDB Isolation:
    • Per-tenant tables or partition keys scoped by tenant
    • IAM policies: restrict access by tenant
    • On-demand pricing: auto-scale per tenant
  • Lambda + API Gateway:
    • Lambda authorizers validate tenant context from JWT
    • Tenant ID passed to Lambda, enforced in code
    • Cost: pay per invocation, built-in isolation

  • Compliance: Data residency (EU data in EU zones), audit logs per tenant
Best Practices
  • Start with namespace isolation, upgrade to cluster if needed
  • Always enforce RBAC + Network Policy (defense in depth)
  • Use row-level security in database, not just app-level checks
  • Track tenant context in logs/traces (tenant-id in every event)
  • Regularly audit isolation (pentest, code review for tenant-id checks)
  • Have a runbook for tenant data exfiltration response
  • Use service mesh for mutual TLS (Istio/Linkerd) between tenant services
Common Pitfalls
  • Forgot to check tenant_id in query: Query returns all data, not just tenant's
  • Cross-tenant leaks in logs: Logs contain PII from wrong tenant
  • Shared secrets: All tenants use same API key → isolation bypassed
  • Over-provisioning: Reserve resources per tenant, but waste them
  • Runaway costs: One tenant's spike is everyone's problem (noisy neighbor)
  • Migrations are slow: Schema changes affect all tenants (rolling upgrade required)
Say this first "Multi-tenancy means one app serves multiple customers with logical or physical separation. You isolate at namespace level (cheap, shared cluster), database level (moderate, separate DBs), or cluster level (expensive, strong isolation). Always use RBAC, network policies, and row-level security to prevent cross-tenant leaks."

"Multi-cluster Strategy: Federation, Mesh, and Load Balancing"

When a single cluster isn't enough (cost, resilience, compliance), I deploy multiple clusters. The challenge is: how do services in cluster-1 talk to services in cluster-2? I can use cluster federation for automatic service discovery, a service mesh (Istio multi-cluster) for traffic management, or a global load balancer. Each has tradeoffs in complexity, latency, and operational overhead.

ArchitectureScaling across clusters›
Cluster Federation (Kubernetes API level)
  • What it does: Services in cluster-1 can be discovered and called from cluster-2 using standard Kubernetes DNS
  • How: A federation control plane syncs Services and Endpoints across clusters
  • Pros: Native Kubernetes, automatic failover, simple mental model
  • Cons: Operational overhead, network latency across clusters, complex debugging
  • Use when: You have 2-3 clusters and need automatic failover
Service Mesh (Istio multi-cluster)
  • What it does: Each cluster runs Istio, and they share a control plane or sync configuration
  • Traffic control: Istio VirtualService can route traffic across clusters with canary, failover, or load-balancing policies
  • Pros: Fine-grained traffic control, mTLS across clusters, circuit breakers at cluster boundaries
  • Cons: High complexity, service mesh overhead on both clusters, steep learning curve
  • Use when: You need sophisticated traffic policies and have teams comfortable with Istio
Global Load Balancer + DNS
  • What it does: Azure Traffic Manager or AWS Route 53 routes traffic to services in different clusters
  • How: DNS resolves service.myapp.com to an IP in cluster-1 or cluster-2 based on health checks
  • Pros: Simplest, no cluster-to-cluster networking, cloud-native
  • Cons: Coarse-grained (cluster-level, not service-level), no automatic failover of individual services
  • Use when: You have independent services and want simplicity over sophistication

Common Pitfalls
  • Over-engineering: Start with global LB, add federation/mesh only if needed
  • Network latency: Cross-cluster calls are slower; minimize them with local caching
  • Split-brain: If clusters lose connectivity to each other, which one is authoritative?
  • Secrets sync: How do you keep secrets consistent across clusters? (Don't manually copy!)

I always ask: can we redesign to avoid cross-cluster calls?"

"Advanced Observability: SLI, SLO, SLA, Error Budgets"

Observability isn't just metrics and logs—it's about understanding service reliability through SLIs (measurable indicators), SLOs (objectives we commit to), and error budgets (how much we can fail). I use this framework to decide when to deploy (within error budget?) and when to stop and stabilize.

ReliabilityMeasurement and decision-making›
SLI (Service Level Indicator)
  • What: A measurable metric that reflects user experience (e.g., 99.9% of requests complete in <500ms)
  • Examples: request latency, error rate, throughput, data freshness
  • Key point: Pick SLIs that matter to users, not just what's easy to measure
  • Example metrics:
    • Availability: (successful requests) / (total requests)
    • Latency: percentage of requests under 500ms
    • Error rate: percentage of 5xx errors
SLO (Service Level Objective)
  • What: A target we commit to for each SLI (e.g., "99.9% availability monthly")
  • Why separate from SLI? SLI is the measurement, SLO is the promise
  • How to set: Talk to users and leadership. "What uptime do customers expect?"
  • Examples:
    • Availability: 99.9% (three nines = 8.64 minutes downtime/month)
    • Latency: 99% of requests <500ms
    • Error rate: 99.95% success rate
  • Avoid: Don't set SLOs you can't meet consistently. (99.999% is only achievable if you have serious multi-region redundancy)
Error Budget
  • What: How much we're allowed to fail while still meeting SLO (1 - SLO)
  • Formula: If SLO is 99.9%, error budget is 0.1% of requests/time
  • Practical:
    • 99.9% monthly = 43.2 minutes of downtime allowed
    • 99.95% monthly = 21.6 minutes allowed
  • How to use: If we've had 30 minutes of downtime this month, we've burned the budget. Stop deploying risky changes and stabilize.
  • Deployment decision: "Is this change risky? Do we have error budget left?"

Advanced Observability Tools
  • Prometheus + custom metrics: Track business metrics (signups/hour, revenue), not just infrastructure
  • Jaeger distributed tracing: Trace a single request across microservices to find bottlenecks
  • Alert fatigue reduction: Use error budget alerts, not just "CPU > 80%". Only alert when SLO is at risk.
  • Anomaly detection: Machine learning to spot gradual degradation (e.g., latency creeping up 1ms/day)
Say this in interview "I use SLI/SLO/error budgets to measure reliability and make deployment decisions. If we have error budget left, we deploy. If we're burning budget, we focus on stability. This objective framework prevents arguments like 'is 99% good enough?' We measure what matters to users and decide based on data."

"Secrets Rotation & Certificate Management"

Static secrets stored in vaults are better than hardcoded, but rotating them manually is a compliance nightmare. I automate rotation so database passwords, API keys, and certificates update without manual intervention. The key is: rotation shouldn't break running services.

SecurityAutomated rotation & zero-downtime updates›
Secrets Rotation Strategies
  • Immediate rotation: Change the secret, update consumers immediately. Risk: apps crash if they re-read the old secret from cache
  • Dual credentials (recommended): Create new secret, keep old one active. Apps can use either. After a grace period (e.g., 24h), deactivate old one. No downtime.
  • Lazy rotation: Create new secret but don't deactivate old until the old one expires naturally (e.g., 90-day cert)
Database Password Rotation (Azure/AWS)
  • Azure Key Vault: Enable automatic rotation. KV generates new password, updates the database, stores new password in vault. Apps fetch from vault on each connection or periodically.
  • AWS Secrets Manager: Lambda function rotates password. Process: generate new password → validate with database → update secret → cleanup old password.
  • Critical: Use connection pooling so apps don't exhaust connections during rotation
  • Timing: Rotate during low-traffic windows to minimize errors
Certificate Rotation (mTLS, HTTPS)
  • Manual nightmare: Admin tracks expiration dates, manually renews, distributes new certs, restarts services. Errors happen.
  • Automated (with cert-manager in K8s): cert-manager watches certificate expiration and auto-renews before expiry. The Ingress automatically uses new cert. No manual intervention.
  • For service mesh (Istio): Istio manages mTLS certificates automatically. Each service gets a cert, Istio renews it before expiry.
  • ACME (Let's Encrypt): Free TLS certs with automatic renewal. cert-manager integrates with ACME so you get free TLS + auto-renewal.
API Key & Token Rotation
  • Third-party API keys: Generate new key in the external service, update apps, revoke old key after verification
  • JWT tokens: Short-lived tokens (1h) + refresh tokens (7d). Apps refresh automatically. If key is compromised, old tokens expire anyway.
  • Service account keys (K8s, cloud): Use workload identity (OIDC) instead. No static key to rotate.
Rotation Failures & Observability
  • Monitor rotation: Alert if rotation job fails. Check logs for why.
  • Grace period: If rotation fails, old secret stays valid for a grace period so apps don't break immediately
  • Rollback plan: If rotation corrupts the secret, can we quickly revert? Keep previous secret for N hours.
  • Test rotation: Manually rotate in staging first, verify apps don't break
Say this in interview "I automate secrets rotation using dual credentials—create new secret, keep old active, then deactivate after a grace period. For certificates, I use cert-manager so they auto-renew. For database passwords, I rotate them in the vault and apps pick up the new one on next connection. The key principle: rotation should be transparent to apps. I always test in staging first."
