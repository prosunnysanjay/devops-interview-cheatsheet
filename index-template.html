Fundamentals

Fundamentals

What's the difference between RUN, CMD, and ENTRYPOINT?

These three are often confused. RUN executes during build, CMD sets default command, ENTRYPOINT is what actually runs. Understanding this is critical for container execution.

Q&ABuild vs runtime›
RUN
  • Executes during image build (not at runtime)
  • Creates a new layer
  • Example: RUN apt-get install -y nginx
  • Used for: installing packages, setting up environment
CMD
  • Sets default command when container runs
  • Can be overridden by docker run arguments
  • Example: CMD ["python", "app.py"]
  • Used for: default behavior if no command specified
ENTRYPOINT
  • The main executable when container starts
  • Cannot be easily overridden
  • Example: ENTRYPOINT ["python", "app.py"]
  • Used for: making container behave like an executable
Key Difference
  • RUN: build time → creates layers
  • CMD: runtime → can be overridden
  • ENTRYPOINT: runtime → main process (PID 1)
Say this in interview "RUN executes during build and creates layers. CMD sets the default command at runtime but can be overridden by docker run. ENTRYPOINT is the main process that runs when container starts. I use ENTRYPOINT for the main app and CMD for default arguments."
Fundamentals

How do you handle environment variables in Dockerfile?

Environment variables configure containers for different environments. There are multiple ways to set them, each with tradeoffs.

Q&AENV, ARG, and runtime›
ENV (Environment Variables)
  • Set at build time, persists in container at runtime
  • Can be overridden with docker run -e
  • Example: ENV DATABASE_URL=localhost:5432
  • Used for: configuration that doesn't change per environment
ARG (Build Arguments)
  • Only available during build, not at runtime
  • Pass with: docker build --build-arg VERSION=1.0
  • Example: ARG VERSION=latest
  • Used for: build-specific settings (not runtime config)
Runtime Override
  • docker run -e LOG_LEVEL=debug (override single var)
  • docker run --env-file .env (load from file)
  • Override ENV from Dockerfile at runtime
Say this in interview "Use ENV for configuration that might differ per environment (dev vs prod). Use ARG for build-time settings only. At runtime, override with -e flag or --env-file. Never hardcode secrets in ENV — use external secret management instead."

Image Optimization

Optimization

What's a multi-stage build? When do you use it?

Multi-stage builds dramatically reduce image size by separating build dependencies from runtime. This is how production images should be built.

Q&ABuild vs runtime stages›
What It Does
  • Multiple FROM statements in one Dockerfile
  • Build dependencies in stage 1, only runtime artifacts in stage 2
  • Final image only contains what's needed to run
Example (Go app)
# Stage 1: Build
FROM golang:1.20 AS builder
WORKDIR /app
COPY . .
RUN go build -o app

# Stage 2: Runtime (minimal)
FROM alpine:latest
COPY --from=builder /app/app .
CMD ["./app"]
Size Reduction
  • Without multi-stage: 800MB (includes Go compiler, build tools)
  • With multi-stage: 50MB (only the binary)
  • 16x smaller image!
When to Use
  • Always for compiled languages (Go, Java, Rust, C++)
  • When build dependencies != runtime dependencies
  • When you need to keep images small for fast deployment
Say this in interview "Multi-stage builds let me separate build dependencies from runtime. Builder stage has compilers and tools, final stage only has the binary. This reduces image size from 800MB to 50MB. I always use this for compiled languages."
Optimization

How do you optimize a Docker image for size?

Smaller images mean faster deployments, less storage, faster pulls from registry. Multiple strategies to reduce bloat.

Q&APractical techniques›
Start with Small Base Image
  • alpine:latest (5MB) vs ubuntu:latest (77MB)
  • Use distroless images (Google) for production (20-50MB)
  • Example: gcr.io/distroless/base (just LIBC + app)
Layer Optimization
  • Combine RUN commands to reduce layers: RUN apt update && apt install -y pkg1 pkg2 && apt clean
  • Clean up package managers: rm -rf /var/lib/apt/lists/*
  • Each layer adds overhead
Multi-stage Builds
  • Separate build stage from runtime stage
  • Build stage: includes compiler, build tools, dependencies
  • Runtime stage: only the final binary/artifacts
  • Copy only needed artifacts from builder to runtime: COPY --from=builder /app/app .
  • Biggest impact for compiled languages (Go, Java, Rust)
  • Can reduce 800MB image to 50MB
.dockerignore
  • Exclude unnecessary files: .git, node_modules, tests, docs
  • Reduces build context size
Say this in interview "Start with alpine or distroless base images. Use multi-stage builds. Combine RUN commands to reduce layers. Clean up package managers. Use .dockerignore to exclude unnecessary files. These techniques together can reduce images by 80%."
Optimization

Your Docker image is 2GB. How do you reduce it?

2GB is huge. This is a practical troubleshooting scenario where you need to find and eliminate bloat.

ScenarioDebugging oversized images›
Step 1: Identify What's Taking Space
# Use docker inspect to see layers
docker inspect --format='{{json .RootFS.Layers}}' image-name

# Use dive tool for detailed layer analysis
dive image-name

# Manual investigation
docker run --rm -it image-name bash
du -sh /* | sort -h  # Find largest directories
Common Culprits
  • /var/cache (package manager cache) - 500MB+
  • /tmp (build artifacts left behind) - 300MB+
  • /root/.npm or /root/.m2 (dependency caches) - 400MB+
  • Multiple copies of files (COPY in multiple layers)
  • Unnecessary build tools in final image
Fixes
  • Clean package managers: apt clean && rm -rf /var/lib/apt/lists/*
  • Clear caches: rm -rf /tmp/* /root/.npm /root/.m2
  • Use multi-stage build to exclude build deps
  • Switch to alpine base image
  • Use .dockerignore to exclude large directories
Example Dockerfile Fix
FROM node:18
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production && npm cache clean --force
COPY . .
RUN rm -rf /tmp/* /var/log/* /var/cache/*
# Result: 1GB → 400MB
Say this in interview "First, I use 'dive' or docker inspect to find what's taking space. Usually it's package caches or build artifacts. I clean those up with rm -rf. Then I switch to alpine base, use multi-stage builds, and optimize layers. This usually gets 2GB down to 400-500MB."
Optimization

How do you optimize build time for Docker images?

Slow builds block CI/CD pipelines. Multiple strategies to speed up builds.

Q&ACaching and parallelization›
Leverage Layer Caching
  • Docker caches layers. If nothing changed, layer is reused.
  • Put frequently changing files last in Dockerfile
  • Example: Install deps first, then COPY source code
  • Bad: COPY . . then RUN npm install (cache bust on any file change)
  • Good: COPY package.json . then RUN npm install then COPY . .
Buildkit (Docker BuildKit)
  • docker buildx build (newer, parallel build stages)
  • Parallelizes independent layers
  • Faster cache lookups
  • Enable: export DOCKER_BUILDKIT=1
.dockerignore
  • Exclude files so they don't get sent to docker daemon
  • Smaller build context = faster
Multi-stage for Build Cache
  • Builder stage caches dependencies
  • If source code changes, dependencies don't rebuild
Say this in interview "Order Dockerfile commands by change frequency: stable things first (OS updates, package installs), then dependencies (package.json), then source code. Use BuildKit for parallelization. Exclude unnecessary files with .dockerignore. These reduce build time from 10 minutes to 2 minutes."
Optimization

What's the impact of running multiple services in one container?

One container = one process. Running multiple services violates Docker principles and causes operational headaches.

Anti-patternWhy this is bad›
Problems with Multiple Services
  • No isolation: If one service crashes, whole container dies
  • Hard to scale: Want to scale web server but not DB? Impossible in one container
  • Complex logging: Logs from both services mixed together, hard to parse
  • Resource management: Can't limit resources per service
  • Startup order: Service A must start before B. Fragile.
  • Health checks: Which service determines container health?
Example: Bad
Dockerfile:
# Runs both Nginx and Python app in one container!
RUN apt install -y nginx python3
ENTRYPOINT ["/bin/bash", "start.sh"]

start.sh:
service nginx start
python app.py
Example: Good
  • One Dockerfile per service
  • One container per service (or pod in K8s)
  • Orchestrate with docker-compose or Kubernetes
Exception: Sidecars
  • In Kubernetes, pods can have multiple containers (sidecar pattern)
  • Main container (app) + sidecar (logging, monitoring)
  • Sidecars are lightweight, not full services
Say this in interview "One service per container. If you need multiple services, use docker-compose or Kubernetes to orchestrate them. Multiple services in one container violates the principle of isolation, makes scaling hard, and complicates logging and health checks. Exception: sidecars in K8s are okay for lightweight helpers."

How do you view logs from a running container?

Logs are your first tool for debugging. Know multiple ways to access them.

Q&ADebugging container output›
Basic Commands
  • docker logs container-name (view all logs)
  • docker logs -f container-name (follow logs, like tail -f)
  • docker logs --tail 50 container-name (last 50 lines)
  • docker logs --since 2024-01-20 container-name (since timestamp)
Interactive Shell
  • docker exec -it container-name bash (attach shell)
  • Then: tail -f /var/log/app.log (view logs from inside)
  • Or: cat /var/log/app.log | grep ERROR
Production: Centralized Logging
  • Don't rely on docker logs for production
  • Send logs to: ELK (Elasticsearch), Loki, Splunk
  • Container logs are lost when container is deleted
Say this in interview "Use 'docker logs -f' to see real-time output. For debugging, docker exec into container and tail the log file. In production, send logs to a centralized system because docker logs are ephemeral—they're deleted when the container stops."
Operations

How do you stop vs kill a container? What's the difference?

Both stop containers, but they work very differently. Understanding this matters for graceful shutdowns.

Q&ASIGTERM vs SIGKILL›
docker stop (Graceful)
  • Sends SIGTERM signal to main process (PID 1)
  • App has 10 seconds to shut down gracefully
  • Close DB connections, save state, clean up
  • After 10 seconds: forcefully kills if still running
  • Used for: normal shutdown
docker kill (Immediate)
  • Sends SIGKILL signal (force kill, cannot be caught)
  • Process has zero chance to clean up
  • Connections abruptly closed, data might be lost
  • Used for: when stop doesn't work, emergency shutdown
Timeline
  • docker stop → SIGTERM → app cleans up (0-10s) → SIGKILL (if timeout)
  • docker kill → SIGKILL immediately
Pro Tip: Handle SIGTERM in App
import signal
import sys

def handle_sigterm(sig, frame):
    print("Shutting down gracefully...")
    # Close DB, save state
    db.close()
    sys.exit(0)

signal.signal(signal.SIGTERM, handle_sigterm)
Say this in interview "'docker stop' sends SIGTERM and waits 10 seconds for graceful shutdown. 'docker kill' sends SIGKILL immediately. Always use stop unless necessary. App should catch SIGTERM to clean up: close connections, save state, finish in-flight requests."
Operations

How do you implement graceful shutdown in a containerized application?

Graceful shutdown prevents data loss and ensures clean termination. Critical for production apps.

Q&ASignal handling & cleanup›
Signal Handling
  • Catch SIGTERM (docker stop sends this)
  • Stop accepting new requests
  • Wait for in-flight requests to complete
  • Close database connections
  • Flush caches, save state
  • Exit cleanly
Example (Node.js)
const http = require('http');
const server = http.createServer((req, res) => {
  res.writeHead(200);
  res.end('OK');
});

let isShuttingDown = false;

process.on('SIGTERM', async () => {
  console.log('SIGTERM received, starting graceful shutdown');
  isShuttingDown = true;

  // Stop accepting new connections
  server.close(() => {
    console.log('Server closed');
    process.exit(0);
  });

  // Force exit after 30 seconds
  setTimeout(() => process.exit(1), 30000);
});

server.listen(3000);
Kubernetes Integration
  • preStop hook: runs before SIGTERM sent
  • terminationGracePeriodSeconds: how long to wait (default 30s)
  • Example: preStop sleep 5s, then drain connections
Load Balancer Integration
  • Remove from LB immediately (no new traffic)
  • Finish existing requests (drain)
  • Close connections to DB
  • Exit after grace period
Say this in interview "Catch SIGTERM in the app. Stop accepting new requests immediately, then wait for in-flight requests to finish (up to grace period, e.g., 30s). Close DB connections cleanly. In Kubernetes, use preStop hook to remove from load balancer. This prevents data loss and ensures clean shutdown."

Configuration

Configuration

How do you handle application configuration in Docker (dev vs prod)?

Different environments need different configs. The wrong approach leads to hardcoding and security issues.

Q&AEnvironment-specific configs›
Bad Approaches
  • Hardcoding configs in code (never!)
  • Separate Dockerfiles per environment (duplicates)
  • Storing secrets in Dockerfile (HUGE security risk)
Good Approach: Environment Variables
  • One Dockerfile for all environments
  • Use ENV in Dockerfile for defaults
  • Override at runtime with: docker run -e VAR=value
  • Example: ENV LOG_LEVEL=info (can override to debug)
Better: Config Files + Env Variables
  • COPY config.yaml into image
  • App reads config.yaml, substitutes env vars
  • At runtime, mount different config.yaml for each env
  • Example: docker run -v prod-config.yaml:/app/config.yaml
In Kubernetes
  • ConfigMaps for non-sensitive config
  • Secrets for passwords, API keys, tokens
  • Mounted as env vars or files into pod
  • Different ConfigMaps per environment (dev, staging, prod)
Say this in interview "Single Dockerfile for all environments. Use environment variables to override defaults. Don't hardcode secrets—use external secret management (K8s Secrets, Vault). In Kubernetes, use ConfigMaps for settings and Secrets for sensitive data. Mount different configs per environment."
Configuration

How should you handle secrets in Docker containers? (Don't hardcode them!)

Secrets are passwords, API keys, tokens. Hardcoding them is a critical security risk. Multiple safe approaches exist.

SecurityDon't hardcode secrets!›
NEVER Do This
  • RUN export DATABASE_PASSWORD=mysecret123 (baked into image)
  • COPY secret.txt into image (visible in docker history)
  • Commit secrets to Git
  • Print secrets in logs
Option 1: Environment Variables at Runtime
  • docker run -e DB_PASSWORD=$(cat secret.txt) app
  • Secret not in image, only in running container
  • Still visible in docker inspect and logs (not ideal)
Option 2: Docker Secrets (Swarm Mode)
  • docker secret create db_pass secret.txt
  • docker service create --secret db_pass app
  • Mounted as files in /run/secrets/db_pass
  • More secure than env vars
Option 3: External Secret Management (Best)
  • HashiCorp Vault, AWS Secrets Manager, Azure Key Vault
  • App fetches secrets at runtime from vault
  • Secret never stored in image or container
  • Can rotate without redeploying
  • Audit trail of who accessed what
Option 4: Kubernetes Secrets
  • kubectl create secret generic db-pass --from-literal=password=xxx
  • Mount as volume or env var in pod
  • Encrypted at rest (if configured)
Say this in interview "Never hardcode or bake secrets into Docker images. Best practice: app fetches secrets from external vault (AWS Secrets Manager, Azure Key Vault) at runtime. In Kubernetes, use Secrets objects. In Docker Swarm, use docker secrets. Always rotate secrets regularly and audit access."

Security

Security

Explain Docker image scanning. Why is it important?

Image scanning finds vulnerabilities in dependencies before they reach production. Automated security defense.

SecurityVulnerability detection›
What It Does
  • Scans all layers, finds installed packages
  • Compares against CVE database (NVD, Snyk, Trivy)
  • Reports known vulnerabilities with severity (critical, high, medium, low)
  • Blocks deployment if critical vulns found
Why It Matters
  • Dependencies have CVEs (Log4j, OpenSSL, etc.)
  • If image has vulnerable library, production is at risk
  • Automated scanning catches this before humans ship it
  • Can be enforced in CI/CD pipeline (fail build if critical CVE)
Tools
  • Trivy (free, fast): trivy image myimage:latest
  • Snyk: online scanning, detailed reports
  • Grype: free vulnerability scanner
  • Docker Scout (built-in): docker scout cves myimage:latest
In CI/CD Pipeline
  • After image build, scan it
  • If critical CVE found, fail the build
  • Developer fixes (update dependency, patch)
  • Rebuild and rescan
  • Example: trivy image --exit-code 1 --severity CRITICAL myimage
Say this in interview "I scan images with Trivy or Docker Scout to find vulnerable dependencies. Scanning happens in CI/CD—if critical CVE found, the build fails. Developer updates the dependency and rebuilds. This prevents vulnerable images from reaching production."
Security

What's the principle of running containers as non-root?

Running as root means if container is compromised, attacker gets root access to host. Running as non-root limits blast radius.

SecurityLeast privilege principle›
Why Not Root
  • Root in container = root on host (in many setups)
  • If app is compromised, attacker has full control
  • Can modify files, install backdoors, escalate privileges
How to Run as Non-root
  • In Dockerfile: RUN useradd -m appuser
  • Then: USER appuser
  • Container runs as appuser, not root
Example Dockerfile
FROM python:3.10
RUN useradd -m appuser
WORKDIR /app
COPY app.py .
RUN chown -R appuser:appuser /app
USER appuser  # Switch to non-root
CMD ["python", "app.py"]
In Kubernetes
  • securityContext.runAsNonRoot: true (enforces non-root)
  • securityContext.readOnlyRootFilesystem: true (extra hardening)
  • Pod won't start if image's USER is root
Say this in interview "Always run containers as non-root. Create a user in Dockerfile (useradd), then USER to switch. In Kubernetes, enforce with securityContext.runAsNonRoot: true. This limits damage if the container is compromised."
Security

How do you implement least privilege for container permissions?

Least privilege: give containers only the permissions they need. Nothing more.

SecurityMinimize blast radius›
File System Permissions
  • Read-only filesystem (except /tmp, /var/run)
  • Don't give write access to /
  • Specific mount points for write (volumes)
Capabilities (Linux Kernel)
  • Containers run with subset of kernel capabilities
  • Default: NET_BIND_SERVICE, SYS_CHROOT, SETFCAP
  • Drop: CAP_SYS_ADMIN (can't change system settings)
  • Docker example: docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE
Kubernetes securityContext
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
  - name: app
    image: myapp:latest
    securityContext:
      runAsNonRoot: true
      readOnlyRootFilesystem: true
      allowPrivilegeEscalation: false
      capabilities:
        drop:
        - ALL
        add:
        - NET_BIND_SERVICE
    volumeMounts:
    - name: tmp
      mountPath: /tmp
  volumes:
  - name: tmp
    emptyDir: {}
Best Practices
  • Run as non-root user
  • Read-only root filesystem
  • Drop all Linux capabilities, add back only what's needed
  • No privilege escalation
  • Regular user (no sudo)
Say this in interview "I implement least privilege by: (1) running as non-root, (2) read-only root filesystem, (3) dropping all Linux capabilities and adding back only NET_BIND_SERVICE, (4) no privilege escalation. In K8s, this is enforced via securityContext. This limits damage if the container is compromised."

Registry

Explain the difference between Docker Hub and private registries

Docker Hub is public, free but not for production. Private registries are for enterprise security and compliance.

Q&APublic vs private storage›
Docker Hub
  • Public registry (hub.docker.com)
  • Free to push (with limits)
  • Official images (nginx, postgres, python)
  • Community images (less vetted)
  • Issue: images publicly visible, rate limiting
  • Good for: learning, open-source projects
Private Registries
  • Azure Container Registry (ACR)
  • AWS Elastic Container Registry (ECR)
  • Harbor, Artifactory (self-hosted)
  • Images are private (not public)
  • Authentication required (credentials, RBAC)
  • Image scanning built-in
  • Good for: production, enterprise, compliance
Comparison
FeatureDocker HubPrivate Registry
VisibilityPublicPrivate
AuthenticationOptionalRequired
Rate limitsYesNo
ScanningBasicAdvanced
CostFree/PaidPaid
RBACLimitedFull
Say this in interview "Docker Hub is public and good for learning. For production, use private registries (ACR, ECR) for security, compliance, and scanning. Private registries require authentication, have better RBAC, no rate limits, and built-in vulnerability scanning."
Registry

How do you tag Docker images? What's the naming convention?

Tags identify image versions. Good tagging practices prevent confusion and enable rollbacks.

Q&AVersioning strategy›
Tag Format
  • registry/repository:tag
  • Example: myregistry.azurecr.io/myapp:1.0.0
  • registry: where image is stored (Docker Hub, ACR, ECR)
  • repository: image name (myapp)
  • tag: version identifier (1.0.0, latest, dev-abc123)
Tagging Strategy
  • Semantic versioning: 1.0.0 (major.minor.patch)
  • Git commit SHA: dev-a1b2c3d4 (unique per commit)
  • Timestamp: 2024-01-20T10:30:00Z
  • Branch name: main, develop, feature-x
  • latest: moving tag for current version (risky in prod!)
Best Practice (Recommended)
  • Commit SHA for CI/CD builds: myapp:a1b2c3d4
  • Also tag with semantic version: myapp:1.0.0
  • Also tag with branch: myapp:main, myapp:develop
  • latest only for known-good versions (not dev builds)
Example in CI/CD
# Build image with commit SHA
docker build -t myapp:$COMMIT_SHA .

# Tag with semantic version
docker tag myapp:$COMMIT_SHA myapp:1.0.0

# Tag with branch
docker tag myapp:$COMMIT_SHA myapp:main

# Push all tags
docker push myapp:$COMMIT_SHA
docker push myapp:1.0.0
docker push myapp:main
Say this in interview "Tag images with commit SHA for CI/CD (unique, traceable), also tag with semantic version (1.0.0) and branch name. Avoid 'latest' in production unless it's tested. This enables easy rollbacks: know exactly which commit is running."
Registry

What's the difference between tagging and versioning?

Tags and versions are different concepts; understanding the distinction prevents confusion.

Q&ASemantics matter›
Versioning
  • Semantic version: 1.0.0, 2.1.3
  • Follows spec: MAJOR.MINOR.PATCH
  • MAJOR: breaking changes
  • MINOR: backward-compatible features
  • PATCH: bug fixes
  • Managed in source code (package.json, version.txt)
Tagging
  • Identifier for image in registry
  • Can be: 1.0.0, main, a1b2c3d4, latest
  • Multiple tags can point to same image
  • Managed at build/deploy time
Example
  • Code version: 1.0.0 (in package.json)
  • Image tags: myapp:1.0.0, myapp:latest, myapp:a1b2c3d4
  • All three tags point to same image (built from version 1.0.0)
Say this in interview "Versioning (1.0.0) describes the software release. Tagging (myapp:1.0.0) identifies the image in the registry. One version can have multiple tags (myapp:1.0.0, myapp:latest, myapp:main). Tags are pointers to images."

How do you use Docker registries in a CI/CD pipeline?

CI/CD pipelines build, push, and pull images from registries. Knowing the workflow is critical.

Q&ABuild → Push → Deploy›
Typical CI/CD Pipeline
  • 1. Source code pushed to Git
  • 2. CI triggers: build Docker image
  • 3. Scan image for vulnerabilities
  • 4. Push to private registry (ACR, ECR)
  • 5. CD pulls image from registry
  • 6. Deploy to Kubernetes/Docker Swarm
Example GitHub Actions Workflow
name: Build and Push

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v2
    - name: Build image
      run: docker build -t myapp:${{ github.sha }} .

    - name: Scan image
      run: trivy image myapp:${{ github.sha }}

    - name: Login to registry
      run: docker login -u ${{ secrets.REGISTRY_USER }} -p ${{ secrets.REGISTRY_PASS }}

    - name: Push image
      run: docker push myapp:${{ github.sha }}
Authentication
  • Store registry credentials in CI/CD secrets
  • Never hardcode username/password
  • Use service principals or tokens (time-limited)
Say this in interview "CI/CD pipeline builds Docker image, scans it for vulns, pushes to private registry. Credentials stored as secrets (not hardcoded). CD stage pulls from registry and deploys. Use commit SHA for tagging to ensure traceability."

Explain image retention policies. Why delete old images?

Registries have storage costs. Old images pile up; retention policies keep things clean and cheap.

Q&ACost and cleanup›
Why Delete Old Images
  • Storage cost: every image layer costs money in registry
  • Security: old images have unpatched CVEs
  • Compliance: need to delete data after retention period
  • Clutter: hard to find relevant images
Retention Policy Example
  • Keep last 10 tagged releases (1.0.0, 1.0.1, etc.)
  • Keep last 30 days of dev builds (branch builds)
  • Delete untagged images older than 7 days
  • Always keep 'latest' tag (assumed to be current)
ACR Retention Policy Example
az acr retention update \
  --registry myregistry \
  --status enabled \
  --days 30 \
  --untagged-only true

# OR: Keep last 10 versions of each tag
az acr retention update \
  --registry myregistry \
  --status enabled \
  --keep 10 \
  --filters "tag=v*"
Best Practices
  • Automate retention policy (don't manual delete)
  • Archive critical images before deletion
  • Log what was deleted (audit trail)
  • Keep releases longer than dev builds
Say this in interview "Set automated retention policies: keep releases (1.0.0, 1.0.1) indefinitely or for years, delete dev builds after 30 days, delete untagged images after 7 days. This saves storage costs and reduces security surface by removing old, unpatched images."

How do you implement image scanning in a registry?

Registry-level scanning catches vulnerabilities across all stored images, not just new ones.

SecurityContinuous vulnerability detection›
Registry Scanning (vs CI/CD Scanning)
  • CI/CD scanning: scans before push (prevents bad images)
  • Registry scanning: scans all images continuously (catches new CVEs)
  • Example: vulnerability published today for library in your 3-month-old image
  • Registry scanning detects this retroactively
ACR Scanning Setup
  • Enable Defender for Container Registries (Azure Security Center)
  • Automatic scan on push
  • Daily rescans of all images
  • Reports vulnerabilities in portal
ECR Scanning Setup (AWS)
  • Enable Basic image scanning
  • Scans automatically on push
  • Reports in ECR console
  • Enhanced scanning with Inspector (continuous)
Alerts & Policies
  • Alert on new critical CVE in existing image
  • Policy: delete or quarantine image if critical vuln found
  • Block deployment if image failed scanning
  • Audit trail: who deployed what, when
Say this in interview "Enable registry-level scanning to continuously monitor all images. New CVEs are discovered daily—your 3-month-old image might have a vuln published last week. Registry scanning catches this. Set policies to alert or block deployment if critical vuln found."

A Docker build is failing intermittently. How do you debug it?

Intermittent failures are the worst. Could be network, caching, resource exhaustion, or race conditions.

ScenarioTroubleshooting build issues›
First: Reproduce Locally
  • docker build . (multiple times, see if it fails)
  • Add --progress=plain to see detailed output
  • Enable BuildKit: DOCKER_BUILDKIT=1 docker build .
Common Causes
  • Network flakiness: apt-get fails to reach package mirror
  • Layer caching: Docker cached a bad layer
  • Resource exhaustion: Docker daemon out of memory
  • Intermittent dependency: npm install fails to fetch package occasionally
  • Race condition: Concurrent downloads conflict
Debugging Steps
  • 1. Force rebuild: docker build --no-cache .
  • 2. Check output: add -v flag for verbose
  • 3. Isolate: comment out suspicious RUN commands
  • 4. Retry: run 5 times in a row, see if it fails consistently
  • 5. Check logs: docker system events during build
Specific Fixes
  • apt-get failing: Add apt-get update && apt-get install together (single layer)
  • npm failing: npm ci (deterministic, better than npm install)
  • Resource issues: Increase Docker memory limit
  • Caching issues: Use --cache-from to reuse layers
Example Fix
# Bad: separate layers, apt-get cached, might fail on retry
RUN apt-get update
RUN apt-get install -y python3

# Good: combined layer, deterministic
RUN apt-get update && apt-get install -y python3 && apt-get clean
Say this in interview "Reproduce locally first. If intermittent, likely network flakiness (apt-get, npm) or Docker caching. Force rebuild with --no-cache to rule out caching. Combine package updates and installs in one RUN command. Use npm ci instead of npm install for determinism."

Explain your approach to Docker image versioning in a CI/CD pipeline

Version strategy affects deployability, rollback capability, and production safety.

Q&AStrategy and traceability›
My Approach
  • 1. Increment version in code (package.json, version.txt): 1.2.3
  • 2. Build image with commit SHA: myapp:a1b2c3d4
  • 3. Tag with version: docker tag myapp:a1b2c3d4 myapp:1.2.3
  • 4. Tag with branch: docker tag myapp:a1b2c3d4 myapp:main
  • 5. Push all tags
Benefits
  • Commit SHA: unique, traceable to exact code
  • Version (1.2.3): semantic, easy to read
  • Branch tag: latest from main, develop, etc.
  • Can rollback by SHA: docker pull myapp:a1b2c3d4
Example CI Pipeline
#!/bin/bash
VERSION=$(cat package.json | grep '"version"' | cut -d'"' -f4)
COMMIT_SHA=$(git rev-parse --short HEAD)
REGISTRY=myregistry.azurecr.io

docker build -t $REGISTRY/myapp:$COMMIT_SHA .
docker tag $REGISTRY/myapp:$COMMIT_SHA $REGISTRY/myapp:$VERSION
docker tag $REGISTRY/myapp:$COMMIT_SHA $REGISTRY/myapp:${{ github.ref_name }}

docker push $REGISTRY/myapp:$COMMIT_SHA
docker push $REGISTRY/myapp:$VERSION
docker push $REGISTRY/myapp:${{ github.ref_name }}
Say this in interview "I version images with: (1) commit SHA for traceability, (2) semantic version (1.2.3) from source code, (3) branch name for convenience. All point to same image. This enables rollbacks: if 1.2.4 breaks, deploy 1.2.3 or the specific SHA."

How do you handle database migrations in containerized applications?

Migrations must run before or alongside app startup. Timing and coordination are critical.

ScenarioSchema and data changes›
Approaches
  • Option 1: Init container (K8s): runs migration before app starts
  • Option 2: sidecar: migration container alongside app
  • Option 3: entrypoint: migration runs in app container before app starts
  • Option 4: separate job: K8s Job runs migrations, then app Deployment
Best Practice: Init Container (K8s)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    spec:
      initContainers:
      - name: migrations
        image: myapp:1.0.0
        command: ["./migrate.sh"]
        env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: url

      containers:
      - name: app
        image: myapp:1.0.0
        command: ["python", "app.py"]
        # App starts only after init container completes
Or: Separate Job (safer)
  • K8s Job runs migrations to completion
  • Then Deployment starts (assumes DB is ready)
  • Good for: complex migrations, rollback safety
Entrypoint Approach (simpler, riskier)
#!/bin/bash
# entrypoint.sh
set -e

if [ "$RUN_MIGRATIONS" = "true" ]; then
  ./migrate.sh
fi

exec python app.py
Key Principles
  • Migrations must complete before app starts
  • Rollback capability: can downgrade schema if needed
  • Idempotent: safe to run multiple times
  • Monitor migration logs separately
Say this in interview "I use K8s init containers for migrations: migration runs to completion before app starts. Makes rollbacks clean. Alternatively, run migrations as a separate K8s Job before deploying the app. Always make migrations idempotent (safe to run multiple times)."

A container is leaking memory. How do you diagnose and fix it?

Memory leaks cause OOMKilled containers. Diagnosis requires tools; fixes require code changes.

ScenarioDebugging memory issues›
Step 1: Confirm Leak
  • docker stats (view memory usage over time)
  • Memory constantly increases? = leak
  • Memory usage plateaus? = normal
  • In K8s: kubectl top pod (view current memory)
Step 2: Identify the App
  • docker exec -it container-name bash
  • ps aux (list running processes)
  • Which process is using memory? (Python, Java, Node?)
Step 3: Capture Memory Profile
  • Python: memory_profiler, objgraph
  • Node: heapdump, clinic.js
  • Java: jdump, YourKit profiler
  • Take heap dump during leak, analyze in IDE
Example (Python)
pip install memory_profiler

@profile
def process_data():
    large_list = []
    for i in range(1000000):
        large_list.append(i)  # Memory leak: list never freed
    return len(large_list)

# Run: python -m memory_profiler script.py
# Shows memory usage per line
Common Causes & Fixes
  • Global caches: Remove or size-limit them
  • Circular references: Use weakref
  • Unclosed connections: db.close() in finally block
  • Event listeners never removed: Always unsubscribe
  • Dependency version: Upgrade library (might have leak fix)
Prevent in Future
  • Set memory limits: docker run -m 512m (kills if exceeds)
  • Monitor: Prometheus scrape memory_bytes metric
  • Alert: Alert if memory grows past baseline
Say this in interview "Use docker stats to confirm leak (memory increasing over time). Profile the app with memory_profiler (Python) or equivalent. Common causes: unclosed connections, unbounded caches, circular references. Fix the code leak, set memory limits to prevent OOMKilled, monitor in production."
